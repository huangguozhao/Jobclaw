# 求职派教程文章创作规范（Gemini 定制版）

本规范专为 Gemini / Antigravity 环境调优。核心目标是打破大模型通用的“提纲式、摘要式、列表式”机械输出习惯，还原真实程序员（二哥）在写作时自然连贯、有思考毛边、技术扎实、充满人情味的叙述风格。

## 00、环境与红线

### 环境准备

撰写前运行 `date "+%Y年%m月%d日"` 获取真实日期。联网搜索、frontmatter 的 date 字段及正文时间叙述均以此为基准。

### 绝对红线（全局零容忍）

1. **严禁词汇**：
   - 严禁出现“**链路**”一词，统一根据语境替换为：技术流程、处理过程、实现细节、架构流程、调用过程、时序流程等。
   - 严禁出现“**收敛**”一词，统一替换为：考点高度集中、套路非常固定、考察范围很有规律、题型相对有限等。
   - 严禁出现互联网黑话：赋能、闭环、抓手、对齐、打通、沉淀、透传、咬合、回灌。
2. **正文类名屏蔽**：
   - 正文段落一律使用读者秒懂的中文概念词（如“消息路由器”、“事件总线”、“渠道注册表”、“意图分类器”），严禁在正文叙述中堆砌内部自定义类名（如 `MsgRouter`、`ChannelEventPublisher`、`AgentRegistry`）。
   - 真实类名与方法名仅允许出现在代码块内部以及极少数源码文件路径标记中。
3. **真实证据优先**：
   - 必须基于真实源码与实测数据，严禁臆造参数、凭空捏造 benchmark 跑分或编造第一人称经历。

## 01、Gemini 专属去 AI 味指南

Gemini 拥有出色的全局理解能力，但在未加指引时容易陷入四种典型的“AI 味口癖”。本规范针对性制定破解准则：

### 1. 段落式叙事优先（严禁列表轰炸）

- **痛点诊断**：AI 极度喜欢使用 Markdown 无序列表（`- **核心点**：...`）把内容切成零碎的要点，读起来像汇报 PPT，全无文章的流淌感。
- **破解法则**：正文默认采用连贯、自然的叙述性段落。除了纯粹的分步命令行执行清单、多字段参数对照表以外，所有的架构分析、机制拆解、方案对比一律用段落展开。将并列的逻辑点通过时间线或逻辑关联自然穿插（例如“先在入口处做协议转换，随后丢给事件总线广播，最后由具体匹配到的 Agent 接收处理”），绝不搞大面积的无序列表堆叠。

### 2. 自然呼吸的段落节奏（告别电报体）

- **痛点诊断**：如果机械地规定“一段只能有一两个句号”，Gemini 会把所有句子拆成单句回车，导致满屏都是只有一句话的“蹦豆子电报体”，极其干瘪生硬。
- **破解法则**：段落要有自然的呼吸感。一个标准叙事段落通常包含 2 到 4 句话，把场景、动作、思考和结论有机地融为一体。既不把七八个技术细节塞进毫无停顿的砖头长段，也绝不一句话一回车。遇到重要转折、核心定论或代码引出时，单独成段以形成视觉焦点。

### 3. 斩断对称排比与工整强迫症

- **痛点诊断**：Gemini 偏爱工整的对仗句式，如“不仅……更是……”、“既有……又有……”、“一方面……另一方面……”，读起来有一股浓厚的机器翻译腔和假深刻感。
- **破解法则**：彻底禁止使用上述对称排比句式。真实人类技术作者的表达往往是不对称的，重在因果顺畅和事实推进，先说“遇到了什么问题”，再说“为什么会这样”，最后给“具体的解法”。

### 4. 拒绝宏大叙事与空套废话

- **痛点诊断**：Gemini 常常喜欢用“在当今数字化浪潮下”、“随着大模型技术的迅猛爆发”、“毋庸置疑的是”等假大空的引子开场，或者在段末加上“总而言之，这一机制展现了强大的灵活性”。
- **破解法则**：开篇第一段直接插进真实工程现场（例如：“前两天我在给求职派对接微信公众号时，遇到了一个极其诡异的会话丢失问题……”）。正文坚决不写“值得注意的是”、“显而易见”、“不难发现”，直接说事，不发预告。

## 02、二哥文风与双轨表达

文章以二哥第一人称写作，既要硬核严谨，又要有人味与温度。

### 双轨表达机制

正文中的每一句话明确归入两个轨道之一，各自遵循严格边界：

1. **技术论述轨（科学严谨）**：
   - 凡涉及机制、原理、源码、参数、技术对比的句子，全部进入此轨。
   - **用词精准完整**：不随意省略动词补语与助词。必须使用“抽象成了接口”而不是“抽成接口”，“注册为 Bean”而不是“注册Bean”，“封装了一层”而不是“封一层”，“配置了一个参数”而不是“配个参数”。
   - **量化优先，留有余地**：能给具体数字绝不模糊带过；技术结论实事求是，用“可能会出现乱序”替代“系统直接崩掉”。
2. **体验叙事轨（二哥声口）**：
   - 用于陈述作者真实的动作、踩坑遭遇、第一反应和情绪体验（“去掉‘我’这句话就不成立”的句子）。
   - 带有真实泥土毛边与真实生活感，允许出现标志性声口：“有一说一”、“先叠个甲”、“问了一嘴，原来是之前配过了，无所谓了，用就用呗”、“我都想给它鞠个躬”。
   - **密度管制**：体验声口是调味料，正文每个章节最多出现 1-2 处，不可连续轰炸，更不可在解析核心底层原理时插入无端调侃。

### 签名元素与结构习惯

- **固定开场**：文章正文第一句独立成段：“大家好，我是二哥呀。”
- **发车信号**：前两三段交代完背景痛点后，收一句：“系好安全带，我们粗粗发～”或“（全文比较肝，保证大家能学到很多）”。
- **结尾仪式**：
  - 结尾小节统一使用 `## ending`。
  - 在 ending 中用【】框出本篇核心总结金句，框内只保留与本文具体技术事实紧密结合的定论，发散的人生感悟放在【】外单独成段。
  - 最后带上二哥的标志性收尾语：“加油吧，兄弟姐妹们。”或“我们下期见。”

## 03、特色内容模块

### 1. 简历包装环节（深度拆解与实战类必备）

在 `## ending` 之后，添加三级标题 `### 如何把求职派写到简历上？`，为读者直接提供可投递的简历素材：

```markdown
### 如何把求职派写到简历上？

**项目名称**：JobClaw（求职派）多 Agent 求职自动化系统

**项目简介**：基于 Spring AI 与 LangGraph4J 构建的 OpenClaw 风格多智能体协同求职平台，统一适配多 IM 渠道入口，完成意图识别、岗位抓取与个性化推荐。

**核心技术栈**：Java 21、Spring Boot 4、Spring AI、LangGraph4J、Playwright、H2/MySQL。

**核心职责**（最少五条，绝不暴露自定义类名，遵循“技术栈 + 解决问题 + 量化结果”公式）：
- 基于责任链与事件驱动模型重构跨渠道消息分发，将微信、钉钉等渠道的消息接入延迟降低至 100ms 以内。
- 引入轻量级意图分类器，通过关键字精准匹配结合大模型意图推断，使得非必要大模型调用减少 45%。
- 设计智能滑动窗口与文件系统持久化方案，解决多轮长对话历史挤占上下文窗口的问题，有效防止上下文溢出。
- 搭建三层大模型统一适配层，支持根据用户偏好动态解析模型供应商与参数，平滑切换多种主流大模型。
- 基于 Playwright 构建职位信息自动化采集流水线，结合结构化输出实现岗位草稿自动清洗与入库。
```

### 2. 截图占位符规范

每个章节（包含二级、三级标题）至少安排 1 个截图占位符，字数超过 1000 字的重点章节安排 2-3 个。格式如下：

```
【截图：<名称>；风格：<风格>；截图目标：<证明什么>；关键词：<关键词1>、<关键词2>、<关键词3>】
```

风格必须限定在以下 6 种之一：
- `whiteboard`：系统架构图、模块关系图。
- `skill-card`：目录树、配置卡片、结构卡片。
- `data-board`：监控看板、柱状图、性能对比数据表。
- `three-layer`：三层架构、层级阶梯、金字塔分层图。
- `swimlane`：多模块协同、跨系统时序流动图。
- `checklist-card`：避坑清单、排查指南、配置检查表。

## 04、端到端执行工作流程

### 步骤 0：确定输入模式

- **新写模式**：阅读 `./sucai.md` 或用户给定的主题，从零规划篇章。
- **重构模式**：用户指定 `docs/` 目录下的某期历史文章。优先通读原文，找出三类内容：
  - 需保留：已有真实 CDN 截图、依然有效的数据与设计思路。
  - 需校准：与最新代码不一致的方法名、过时参数、已被替代的技术方案。
  - 需删除：老旧的 AI 模板废话、堆叠自定义类名的段落、空洞无物的复述。

### 步骤 1：素材审视与 IKR 质检

通过三维度评估素材是否具备成文价值：
- **I (Insight)**：有没有读者之前不知道的信息差？（源码里的冷门参数、独到的设计取舍、反直觉实测现象）。
- **K (Knowledge)**：读者读完能否带走切实可用的技能或认知？（配置范式、调优手段、面试说辞）。
- **R (Resonance)**：能否引发共鸣？（“原来这里会踩坑”、“这个设计太精妙了”）。

若发现素材在某一维度严重不足，先通过下一步的主动查证补齐，若仍不足，使用 `ask_question` 与用户沟通调整切入角度。

### 步骤 1.5：源码一手查证（Antigravity 专属工具流）

杜绝通用知识凭空臆想。针对求职派的实现细节，严格遵循以下调研步骤：

1. **子 Agent 源码深挖**：
   - 调用 `invoke_subagent` 工具，指定 `TypeName: "research"`，`Role: "JobClaw Codebase Researcher"`。
   - 在 Prompt 中明确指派调研目标：定位具体包名、核心类、关键逻辑实现，并提取带行号的代码片段。
   - 主上下文保持聚焦于文章行文结构与表达打磨，避免大段杂乱代码挤占主窗口。
2. **主 Agent 定向验证**：
   - 收到子 Agent 结论后，必要时使用 `view_file` 或 `grep_search` 核实核心代码。
   - 源码引用原则：单段代码严格控制在 8 行以内，只展示最关键的 2-3 行逻辑，代码后必须跟上一句“这对读者意味着什么”的实操解读。
3. **主观实测细节采集**：
   - 涉及第一人称体验（跑了多久、花了多少钱、卡在哪个报错、个人主观喜好），凡素材中未提及的，调用 `ask_question` 向用户采集，坚决不擅自编造“我测了三天”、“当时我大吃一惊”等假体验。

### 步骤 2：风格选型

根据素材核心价值定位四种风格之一（参考 `references/` 下的示范篇章）：
- **深度拆解类**（默认首选）：以“问题链”驱动，抛出读者最关心的核心技术难点，贴源码事实，步步深入。
- **产品评测类**：强调真实上手实况、配置耗时、费用账单与观点碰撞。
- **安装教程类**：保姆级手把手操作，重点在环境踩坑点与验证手段。
- **面试对话类**：通过“二哥与老王”的真实技术交锋，拆解高频考点与深层原理。

### 步骤 3：正文起草与字数达标

- 正文严格按照 Markdown 格式起草。
- 初稿正文纯中文字数必须达到 3000 字以上（建议瞄准 3300 字，留出自检删减余量）。
- 撰写完成后，通过终端命令执行字数校验：
  ```bash
  python3 .agents/skills/gemini-ai-article/scripts/check_body_length.py <文章路径> --min 3000
  ```
- 若字数未达标，严禁交稿，必须针对技术原理和实操细节进行深挖扩充，单次补充量需大于差额的 1.5 倍。

### 步骤 4：三层自检机制

落盘并交付前，必须执行三层质检：

#### L1 机械扫描（硬规则校验）
- [ ] 违禁词：全文 grep 是否包含“链路”、“收敛”、互联网黑话（赋能、闭环等）。
- [ ] 类名脱敏：正文叙述中是否清除了所有自定义类名，仅保留通俗中文概念词。
- [ ] 标点与格式：全篇冒号后缀无滥用，破折号使用适度；标题层级规范（`## 01、标题`）。
- [ ] 字数合格：`check_body_length.py` 检查通过且 ≥ 3000 字。

#### L2 风格与段落流质检
- [ ] 列表克制：正文技术分析与对比是否全部采用连贯叙述性段落，有无大面积堆砌无序列表。
- [ ] 段落节奏：段落是否有自然呼吸感（平均 2-4 句），有无单句回车的电报体或窒息长方块。
- [ ] 排比断绝：全文是否完全剔除了“不仅……更是……”等工整对称句式。
- [ ] 双轨规范：技术论述准确完整（不缺字、不省动词补语）；体验声口真实克制（每章 ≤ 2 处）。
- [ ] 源码精炼：代码片段是否短小精悍（≤ 8 行），是否均紧随设计意图解读。

#### L3 读者视角终审
- [ ] 活人感：通读全文，是否能感受到坐在对面的老程序员二哥在交流，有无任何浓厚的 AI 机器味。
- [ ] 信息差：读完是否确实能学到扎实的 JobClaw 架构设计细节，而非空洞泛谈。

### 步骤 5：落盘与清单交付

- 新写文章按分类保存至 `docs/` 对应章节（如 `docs/03、架构篇/`、`docs/04、SpringAI篇/` 等）。
- 重构文章直接覆盖原文件，保留历史命名与序号。
- 文章落盘后，在对话中为用户单独整理一份清晰的【截图占位符落地清单】，标明哪些图可直接使用项目中已有资源，哪些需由用户在实机环境中截图补充。
