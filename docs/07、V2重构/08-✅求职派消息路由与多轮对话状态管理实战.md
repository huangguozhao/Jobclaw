# ✅求职派消息路由与多轮对话状态管理实战

> 当用户通过 IM 发送一条消息，系统怎么知道该由哪个 Agent 来处理？如果用户连续发多条消息，怎么保证始终由同一个 Agent 响应？用户想切换 Agent 怎么办？这就是消息路由要解决的核心问题。本文完整记录求职派的消息路由机制、意图识别策略与多轮对话状态一致性保证方案。

---

## 一、为什么需要消息路由？

### 1.1 没有路由会怎样？

**场景还原**：

```
用户（通过钉钉）："帮我找北京的国企秋招职位"
```

**没有消息路由的系统**：

```java
// 反例：所有消息走同一个入口
@EventListener
public void onMessage(MessageReceivedEvent event) {
    // 只有一个 LLM 调用，所有消息都一样处理
    String response = llmCaller.call(prompt);
    sendResponse(response);
}
```

**问题**：

| 问题 | 后果 |
|------|------|
| **无分工** | 所有 Agent 能力混在一起，Prompt 越来越臃肿 |
| **无上下文** | 用户问"第二个岗位怎么样"，系统不知道"第二个"指什么 |
| **无切换** | 用户说"帮我设置一个提醒"，系统不知道该切到 TaskAgent |
| **无兜底** | Agent 处理失败时，没有降级策略 |

### 1.2 V2 的设计目标

> **如何让一条消息经过：意图识别 → Agent 路由 → 会话绑定 → Agent 执行 → 响应回写，确保多轮对话始终由正确的 Agent 处理？**

四个核心诉求：

1. **意图识别**：区分"找职位"、"设置提醒"、"修改偏好"等不同意图
2. **Agent 路由**：根据意图找到最合适的 Agent
3. **会话绑定**：多轮对话锁定同一个 Agent，不串台
4. **异常兜底**：Agent 执行失败时自动降级

## 二、消息处理主链路

### 2.1 消息路由的完整流程

```
IM 消息到达
  │
  ▼
MsgRouter.onMessageReceived()          ← 事件监听入口
  │
  ├─ Step 1: 身份检查
  │    identityAgent.triggerToCollectIdentity()
  │    （详见身份采集文档，此处不展开）
  │
  ├─ Step 2: 系统命令处理
  │    commandDispatcher.executeCommand()
  │    （详见 CLI 机制文档，此处不展开）
  │
  ├─ Step 2.5: /agentId 快捷切换
  │    userMessage.startsWith("/") → 遍历匹配 Agent ID
  │
  ├─ Step 3: 检查是否已绑定 Agent
  │    sessionBinder.needsIntentRecognition()
  │    ├─ 已绑定 → 直接 routeToAgent()
  │    └─ 未绑定 → 继续
  │
  ├─ Step 4: 意图识别
  │    intentClassifier.classify()
  │    → CompositeIntentClassifier: 关键词 → LLM
  │
  ├─ Step 5: 路由决策
  │    agentRouter.route()
  │    → IntentBasedAgentRouter: 意图 → Agent 映射
  │
  ├─ Step 6: 会话绑定
  │    sessionBinder.bind()
  │    → 持久化会话-Agent 关系
  │
  └─ Step 7: 执行 Agent
       routeToAgent()
       → agent.process() / agent.stream()
```

### 2.2 MsgRouter 的核心实现

```java
@Component
public class MsgRouter {

    @Async
    @EventListener
    public void onMessageReceived(MessageReceivedEvent event) {
        var msg = event.getOriginalMessage();
        String userMessage = msg.getMessage();
        UserConversationInfo info = new UserConversationInfo(
            msg.getJobClawUserId(), msg.getChannel(), msg.getFromUserId(), msg.isGroupTalk());

        // Step 1: 身份采集（首次用户自动触发）
        if (!msg.isGroupTalk() && identityAgent.triggerToCollectIdentity(info, userMessage)) {
            return; // 进入身份采集流程，中断当前对话
        }

        // Step 2: 系统命令
        if (commandDispatcher.isSystemCommand(userMessage)) {
            commandDispatcher.executeCommand(msg, info, userMessage, this::sendTextResponse);
            return;
        }

        // Step 2.5: 快捷切换 /agentId
        if (userMessage.startsWith("/")) {
            for (BizAgent agent : agentRegistry.getAllAgents(msg.getJobClawUserId())) {
                if (userMessage.startsWith("/" + agent.getAgentIntro().getAgentId())) {
                    routeToAgent(agent.getAgentIntro().getAgentId(), msg, info);
                    return;
                }
            }
        }

        // Step 3: 跳过意图识别（已绑定 Agent）
        if (!sessionBinder.needsIntentRecognition(
                msg.getJobClawUserId(), info.conversationId(), userMessage)) {
            String agentId = sessionBinder.getBoundAgentId(
                msg.getJobClawUserId(), info.conversationId()).orElse(null);
            routeToAgent(agentId, msg, info);
            return;
        }

        // Step 4: 意图识别
        IntentClassificationRes classification = intentClassifier.classify(info, userMessage, List.of());

        // Step 5: 路由决策
        var currentBound = sessionBinder.getBoundAgentId(
            msg.getJobClawUserId(), info.conversationId());
        var routeResult = agentRouter.route(classification, currentBound);

        // Step 6: 会话绑定
        if (routeResult.isNewSession()) {
            sessionBinder.bind(msg.getJobClawUserId(), info.conversationId(), routeResult.agentId());
        }

        // Step 7: 执行 Agent
        routeToAgent(routeResult.agentId(), msg, info);
    }
}
```

**设计要点**：

| 步骤 | 解决的问题 | 关键判断 |
|------|-----------|---------|
| Step 1 | 新用户引导 | `!isGroupTalk() && identityAgent.triggerToCollectIdentity()` |
| Step 2 | 系统命令响应 | `commandDispatcher.isSystemCommand()` |
| Step 3 | 跳过重复识别 | `sessionBinder.needsIntentRecognition()` |
| Step 4-6 | 新会话路由 | `isNewSession()` 决定是否绑定 |

## 三、意图识别：三层分类器

### 3.1 为什么需要三层分类？

**问题**：只用一种方式识别意图，有什么问题？

| 方案 | 问题 |
|------|------|
| **仅关键词** | "帮我看看有什么岗位" → 匹配到"看看"→ 意图是 QUERY？还是 RECOMMEND？关键词有歧义 |
| **仅 LLM** | 每一条消息都调用大模型，成本高、响应慢、对话未绑定前用户多等几秒 |

**解决方案**：三层递进——快路径优先，慢路径兜底。

```
Layer 0: 系统命令    最快        /help, /agents, /reset, /agent xxx
Layer 1: 关键词匹配   中等        匹配预设的关键词表
Layer 2: LLM 识别    最慢(兜底)  调用大模型理解模糊语义
```

### 3.2 CompositeIntentClassifier：组合器

```java
@Component
public class CompositeIntentClassifier implements IntentClassifier {

    private static final double HIGH_CONFIDENCE_THRESHOLD = 0.9;  // 高可信
    private static final double MEDIUM_CONFIDENCE_THRESHOLD = 0.7; // 中可信

    @Override
    public IntentClassificationRes classify(...) {
        // L0: 系统命令匹配（最高优先级）
        Optional<PresetAgentIntro> commandIntent = commandDispatcher.recognizeIntent(message);
        if (commandIntent.isPresent()) {
            return IntentClassificationRes.highConfidence(commandIntent.get(), "命令匹配");
        }

        // L1: 关键词匹配
        IntentClassificationRes keywordResult = keywordClassifier.classify(...);
        if (keywordResult.isHighlyConfident()) {        // >= 0.9: 直接使用
            return keywordResult;
        }
        if (keywordResult.isConfident()) {              // >= 0.7: 可信，直接使用
            return keywordResult;
        }

        // L2: LLM 兜底（关键词置信度 < 0.7 时降级）
        IntentClassificationRes llmResult = llmClassifier.classify(...);
        if (llmResult.isConfident()) {
            return llmResult;
        }

        // 兜底：UNKNOWN
        return IntentClassificationRes.unknown("所有策略均未识别");
    }
}
```

**决策树**：

```
用户消息
  │
  ├─ 以 / 开头 → L0 命令匹配 → 直接返回
  │
  ├─ 关键词匹配 ≥ 0.9 → 直接返回（快路径）
  │
  ├─ 关键词匹配 ≥ 0.7 → 直接返回（中路径）
  │
  ├─ 关键词匹配 < 0.7 → L2 LLM 识别（慢路径）
  │
  └─ LLM 也不确定 → UNKNOWN，路由到默认兜底 Agent
```

### 3.3 KeywordIntentClassifier：关键词匹配

**设计起点**：为什么不用正则表达式？

```java
// 反例：用正则匹配意图
if (message.matches(".*(投递|投简历).*")) {
    return COLLECT;
}
if (message.matches(".*(推荐|帮我看看).*")) {
    return RECOMMEND;
}
```

**问题**：

```
用户说："帮我看看有什么岗位" → 匹配到"帮我看看" → RECOMMEND ✓
用户说："帮我看看我的投递记录" → 匹配到"帮我看看" → RECOMMEND ✗（应该是 QUERY）
```

单个关键词无法消除歧义，需要**权重体系**——多个关键词竞争，最高权重者胜出。

```java
private static final Map<PresetAgentIntro, List<KeywordEntry>> KEYWORDS = Map.of(
    PresetAgentIntro.COLLECT, List.of(
        new KeywordEntry("投递", 1.0),
        new KeywordEntry("投简历", 1.0),
        new KeywordEntry("岗位信息", 0.9),
        new KeywordEntry("面试", 0.7)
    ),
    PresetAgentIntro.RECOMMEND, List.of(
        new KeywordEntry("推荐", 1.0),
        new KeywordEntry("帮我看看", 0.9),
        new KeywordEntry("有什么岗位", 0.8),
        new KeywordEntry("求推荐", 1.0)
    ),
    PresetAgentIntro.QUERY, List.of(
        new KeywordEntry("查询", 1.0),
        new KeywordEntry("查看", 0.8),
        new KeywordEntry("状态", 0.7),
        new KeywordEntry("投递记录", 1.0)
    )
);
```

**匹配策略**：

```
"帮我看看有什么岗位"
  ↓ 扫描所有关键词
  匹配 "帮我看看"(0.9) → RECOMMEND
  匹配 "有什么岗位"(0.8) → RECOMMEND
  ↓
  最高分 0.9 ≥ 0.9 → 高可信，直接返回 RECOMMEND
```

**设计要点**：
- 每个关键词有独立权重，不依赖固定的正则规则
- 多条匹配取最高分，天然支持复合意图消歧
- 0.9 以上直接返回（快路径），0.7-0.9 可信也直接返回（避免 LLM 调用的成本）

### 3.4 LLMIntentClassifier：LLM 兜底

当关键词匹配置信度低于 0.7 时，降级到 LLM 识别：

```java
@Component
public class LLMIntentClassifier implements IntentClassifier {

    private static final String PROMPT_TEMPLATE = """
        您是一个意图分类器，请分析用户的消息意图。

        可分类的意图类型：
        {{BizAgent}}
        - UNKNOWN: 无法确定

        用户消息：{{message}}

        请返回JSON格式的分类结果：
        {
          "intentType": "RECOMMEND",
          "confidence": 0.95,
          "reasoning": "用户请求推荐职位"
        }
        """;

    public IntentClassificationRes classify(...) {
        // 动态获取当前所有可用 Agent，注入到 Prompt
        List<BizAgent> agents = agentRegistry.getAllAgents(userId);
        String prompt = PROMPT_TEMPLATE
            .replace("{{BizAgent}}", formatAgentList(agents))
            .replace("{{message}}", message);

        // 调用 LLM，直接解析为结构化结果
        return simpleLlmCaller.call(info, new Prompt(prompt),
                                    IntentClassificationRes.class);
    }
}
```

**为什么需要把 Agent 列表注入到 Prompt？**

```
Agent 列表是动态的：
  - 不同用户有不同的权限（VIP 用户能看到更多 Agent）
  - 插件可能启用/禁用（PlanNotebook 开启时才有 PLAN Agent）
  - 硬编码 Agent 列表 → 新增 Agent 要改 Prompt

动态注入：
  - Prompt 随 AgentRegistry 变化
  - 新增 Agent 自动出现在 LLM 的可选项中
```

### 3.5 IntentClassificationRes：置信度驱动的结果模型

```java
public record IntentClassificationRes(
    PresetAgentIntro intentType,   // 识别到的意图
    double confidence,             // 置信度 0.0-1.0
    String reasoning,              // 推理过程
    Map<String, Object> context    // 额外上下文
) {
    public boolean isConfident() { return confidence >= 0.7; }
    public boolean isHighlyConfident() { return confidence >= 0.9; }

    public static IntentClassificationRes highConfidence(PresetAgentIntro type, String reason) {
        return new IntentClassificationRes(type, 1.0, reason);
    }
    public static IntentClassificationRes unknown(String reason) {
        return new IntentClassificationRes(PresetAgentIntro.UNKNOWN, 0.0, reason);
    }
}
```

**置信度驱动的设计价值**：

```
置信度 ≥ 0.9: 关键词直接命中，快路径，无需 LLM
置信度 0.7-0.9: 关键词命中但不够强，仍然直接使用（避免 LLM 成本）
置信度 < 0.7: 降级到 LLM，让大模型理解模糊语义
置信度 = 0.0: UNKNOWN，使用默认兜底 Agent
```

## 四、Agent 路由：从意图到 Agent

### 4.1 路由决策的核心逻辑

意图识别完成后，需要回答一个问题：**哪个 Agent 来处理这个意图？**

```java
@Component
public class IntentBasedAgentRouter implements AgentRouter {

    @Override
    public RouterResult route(IntentClassificationRes classification,
                               Optional<String> currentBoundAgent) {
        PresetAgentIntro intentType = classification.intentType();

        // 1. 系统意图不路由到具体 Agent
        if (intentType == PresetAgentIntro.HELP ||
            intentType == PresetAgentIntro.LIST_AGENTS ||
            intentType == PresetAgentIntro.RESET) {
            return new RouterResult(intentType.getAgentId(), true, "系统意图");
        }

        // 2. 如果已绑定 Agent 且支持新意图，保持绑定
        if (currentBoundAgent.isPresent()) {
            String boundAgentId = currentBoundAgent.get();
            if (agentRegistry.isAgentSuitable(boundAgentId, intentType)) {
                return RouterResult.continuing(boundAgentId, "支持新意图，保持");
            }
        }

        // 3. 根据意图查找合适的 Agent
        List<BizAgent> suitableAgents = agentRegistry.getAgentsForIntent(intentType);
        if (!suitableAgents.isEmpty()) {
            BizAgent selected = suitableAgents.get(0);
            boolean isNew = currentBoundAgent.isEmpty() ||
                !currentBoundAgent.get().equals(selected.getAgentIntro().getAgentId());
            return new RouterResult(selected.getAgentIntro().getAgentId(), isNew, "路由匹配");
        }

        // 4. 兜底：使用默认 Agent
        return agentRegistry.getDefaultAgent()
            .map(a -> new RouterResult(a.getAgentIntro().getAgentId(), false, "默认兜底"))
            .orElse(new RouterResult("__unknown__", false, "无可用Agent"));
    }
}
```

**决策树**：

```
意图识别结果
  │
  ├─ 系统意图（HELP/LIST_AGENTS/RESET）→ 不路由，MsgRouter 直接处理
  │
  ├─ 已绑定 Agent + 支持新意图 → 保持当前 Agent（连续性保证）
  │
  ├─ 意图有对应 Agent → 路由到该 Agent
  │     ├─ 与当前绑定不同 → isNewSession=true（重新绑定）
  │     └─ 与当前绑定相同 → isNewSession=false（继续）
  │
  ├─ 意图无对应 Agent → 路由到默认兜底 Agent
  │
  └─ 无默认 Agent → __unknown__（MsgRouter 最后降级）
```

### 4.2 AgentRegistry：Agent 注册中心

#### 为什么需要注册中心？

**问题**：路由决策时怎么知道有哪些 Agent 可用？

```java
// 反例：硬编码 Agent 列表
private List<BizAgent> getAllAgents() {
    return List.of(
        new JobFetchAgent(...),
        new JobRecommendAgent(...),
        new TaskBizAgent(...)
        // 每新增一个 Agent 都要改这里
    );
}
```

**解决方案**：Spring 自动收集 + 注册中心。

```java
public class DefaultAgentRegistry implements AgentRegistry {

    private final Map<String, BizAgent> agents = new ConcurrentHashMap<>();
    private BizAgent defaultAgent;

    // 意图 → Agent ID 映射表（可配置化）
    private static final Map<PresetAgentIntro, List<String>> INTENT_AGENT_MAPPING = Map.of(
        PresetAgentIntro.COLLECT,   List.of("JobFetchAgent", "default"),
        PresetAgentIntro.RECOMMEND, List.of("JobRecommendAgent", "default"),
        PresetAgentIntro.TASK,      List.of("task", "default"),
        PresetAgentIntro.PLAN,      List.of("plan", "default"),
        PresetAgentIntro.DEFAULT,   List.of("default")
    );

    @Override
    public void register(BizAgent agent) {
        agents.put(agent.getAgentIntro().getAgentId(), agent);
        if (PresetAgentIntro.DEFAULT.equals(agent.getAgentIntro())) {
            defaultAgent = agent;
        }
        log.info("注册Agent: {}", agent.getAgentIntro());
    }

    @Override
    public List<BizAgent> getAgentsForIntent(PresetAgentIntro intentType) {
        List<String> agentIds = INTENT_AGENT_MAPPING.get(intentType);
        return agentIds.stream()
            .map(agents::get)
            .filter(Objects::nonNull)
            .sorted(Comparator.comparingInt(BizAgent::getPriority).reversed())
            .collect(Collectors.toList());
    }

    @Override
    public List<BizAgent> getAllAgents(String jobClawUserId) {
        // 按用户权限过滤 Agent
        UserRoleEnum role = userService.getRole(jobClawUserId);
        return agents.values().stream()
            .filter(agent -> agent.permission().enabled(role))
            .collect(Collectors.toList());
    }
}
```

## 五、会话绑定：多轮对话状态一致性保证

### 5.1 为什么需要会话绑定？

**场景**：

```
用户："帮我找北京的国企秋招职位"
  → 意图识别: RECOMMEND → 路由到 JobRecommendAgent
  → JobRecommendAgent: "为您找到以下5个岗位..."

用户："第二个岗位怎么样？"
  → 如果没有会话绑定，重新意图识别:
  → "第二个" → 关键词匹配不到 → LLM 也难理解 → 路由到 DEFAULT Agent
  → 新 Agent 不知道之前的对话上下文
```

**核心问题**：**多轮对话中，状态一致性怎么保证？**

### 5.2 SessionAgentBinder 的设计

```java
public interface SessionAgentBinder {

    /** 绑定会话到指定 Agent */
    void bind(String jobClawUserId, String sessionId, String agentId);

    /** 获取绑定信息（含过期时间） */
    Optional<BoundAgentInfo> getBoundAgent(String jobClawUserId, String sessionId);

    /** 判断是否需要重新意图识别 */
    boolean needsIntentRecognition(String jobClawUserId, String sessionId, String userMessage);

    /** 解除绑定 */
    void unbind(String jobClawUserId, String sessionId);

    record BoundAgentInfo(String agentId, Instant boundAt, Instant expiresAt) {}
}
```

**设计要点**：

| 方法 | 解决的问题 | 调用时机 |
|------|-----------|---------|
| `bind()` | 新会话建立绑定 | 意图识别后、Agent 执行前 |
| `getBoundAgent()` | 获取当前会话的 Agent | 每次消息处理前检查 |
| `needsIntentRecognition()` | 判断是否需要重新识别 | 每次消息处理时调用 |
| `unbind()` | 手动解除绑定 | `/reset`、Agent 切换 |

### 5.3 needsIntentRecognition：跳过意图识别的决策

```java
@Override
public boolean needsIntentRecognition(String jobClawUserId, String sessionId, String userMessage) {
    // 1. 明确的重置指令 → 需要重新识别
    if (userMessage != null && userMessage.trim().toLowerCase().startsWith("/reset")) {
        return true;
    }

    // 2. 不存在绑定 → 需要识别
    if (getBoundAgent(jobClawUserId, sessionId).isEmpty()) {
        return true;
    }

    // 3. 绑定已过期 → 需要识别
    return getBoundAgent(jobClawUserId, sessionId).isEmpty();
}
```

**决策逻辑**：

```
needsIntentRecognition() = true 的情况：
  ├─ 用户发了 /reset
  ├─ 该会话从未绑定过 Agent
  └─ 绑定已过期（默认 6 小时 TTL）

其他情况 = false（跳过意图识别，直接路由到已绑定的 Agent）
```

**为什么需要过期时间？**

```
用户上午和 JobRecommendAgent 聊了 5 轮，绑定了 Agent
  → 下午又发了一条消息
  → 绑定未过期（6 小时内）→ 跳过识别 → 继续使用 JobRecommendAgent ✓

用户一周前绑定过 Agent，今天又发消息
  → 绑定 6 小时已过期 → needsIntentRecognition() = true
  → 重新意图识别 → 路由到新的 Agent ✓
```

### 5.4 FileSystemSessionAgentBinder：文件持久化

#### 设计起点：会话信息存哪里？

```java
// 反例：内存 Map
private final Map<String, BoundAgentInfo> sessionMap = new ConcurrentHashMap<>();
```

**问题**：应用重启后所有会话绑定丢失，用户需要重新绑定 Agent。

**解决方案**：YAML 文件持久化。

**存储结构**：

```
workspace/sessions/
├── {jobClawUserId-1001}/
│   ├── session-chat-xxx.yaml
│   └── session-chat-yyy.yaml
└── {jobClawUserId-1002}/
    └── session-chat-zzz.yaml
```

**文件内容**：

```yaml
---
sessionId: chat-abc123
jobClawUserId: "1001"
boundAgentId: JobRecommendAgent
boundAt: 2026-04-20T09:00:00Z
expiresAt: 2026-04-20T15:00:00Z
---
```

**核心实现**：

```java
@Component
public class FileSystemSessionAgentBinder implements SessionAgentBinder {

    private static final Path SESSION_BASE = Path.of("workspace/sessions");
    private static final Duration DEFAULT_TTL = Duration.ofHours(6);

    @Override
    public void bind(String jobClawUserId, String sessionId, String agentId) {
        bind(jobClawUserId, sessionId, agentId, Instant.now().plus(DEFAULT_TTL));
    }

    @Override
    public void bind(String jobClawUserId, String sessionId,
                     String agentId, Instant expiresAt) {
        Path sessionFile = getSessionFile(jobClawUserId, sessionId);
        SessionState state = loadOrCreate(sessionFile);
        state.boundAgent = new BoundAgentInfo(agentId, Instant.now(), expiresAt);
        save(sessionFile, state);
    }

    @Override
    public Optional<BoundAgentInfo> getBoundAgent(String jobClawUserId, String sessionId) {
        Path sessionFile = getSessionFile(jobClawUserId, sessionId);
        SessionState state = load(sessionFile);
        if (state == null || state.boundAgent == null) return Optional.empty();

        // 过期检查
        if (state.boundAgent.expiresAt().isBefore(Instant.now())) {
            return Optional.empty();
        }
        return Optional.of(state.boundAgent);
    }

    private Path getSessionFile(String jobClawUserId, String sessionId) {
        return SESSION_BASE.resolve(jobClawUserId)
            .resolve("session-" + sessionId + ".yaml");
    }
}
```

### 5.5 意图历史记录

除了当前绑定的 Agent，`SessionAgentBinder` 还记录了意图历史，用于后续的上下文分析和意图切换决策：

```java
@Override
public void addIntentHistory(String jobClawUserId, String sessionId,
                             PresetAgentIntro intentType, double confidence) {
    SessionState state = loadOrCreate(sessionFile);
    state.intentHistory.add(new IntentHistoryItem(intentType, confidence, Instant.now()));

    // 保留最近 10 条
    if (state.intentHistory.size() > 10) {
        state.intentHistory = state.intentHistory.subList(
            state.intentHistory.size() - 10, state.intentHistory.size());
    }
    save(sessionFile, state);
}
```

## 六、多轮对话状态一致性的完整保证

### 6.1 三种场景的状态管理

**场景 1：新用户发送第一条消息**

```
用户："帮我找北京的国企秋招职位"
  │
  ├─ Step 3: needsIntentRecognition() = true（无绑定）
  ├─ Step 4: intentClassifier → RECOMMEND
  ├─ Step 5: agentRouter → JobRecommendAgent
  ├─ Step 6: sessionBinder.bind("1001", "chat-xxx", "JobRecommendAgent")
  └─ Step 7: JobRecommendAgent 执行
```

**场景 2：同一会话继续对话**

```
用户："第二个岗位怎么样？"
  │
  ├─ Step 3: needsIntentRecognition() = false（已绑定，未过期）
  ├─ Step 7: routeToAgent("JobRecommendAgent")
  └─ JobRecommendAgent 继续处理（有对话记忆上下文）
```

**场景 3：用户主动切换 Agent**

```
用户："帮我设置一个明天 9 点的面试提醒"
  │
  ├─ Step 3: needsIntentRecognition() = false（已绑定）
  │   但...用户意图从 RECOMMEND 变成了 TASK
  │
  ├─ Step 7: routeToAgent("JobRecommendAgent")
  │   JobRecommendAgent 收到"设置提醒"，但它没有 TaskTool
  │   → LLM 发现无法处理 → 失败
  │
  └─ 【问题】已绑定的 Agent 不支持新意图怎么办？
```

### 6.2 隐式切换的处理

AgentRouter 的 `shouldKeepAgent()` 逻辑：

```java
// IntentBasedAgentRouter
@Override
public boolean shouldKeepAgent(String currentAgentId, PresetAgentIntro newIntentType) {
    // 系统意图不保持
    if (newIntentType == PresetAgentIntro.HELP ||
        newIntentType == PresetAgentIntro.RESET) {
        return false;
    }
    // 检查当前 Agent 是否支持新意图
    return agentRegistry.isAgentSuitable(currentAgentId, newIntentType);
}
```

当已绑定的 Agent 不支持新意图时，`needsIntentRecognition()` 返回 false 但 Agent 执行失败。这时 MsgRouter 的异常捕获机制介入：

```java
private void routeToAgent(String agentId, ..., UserConversationInfo info) {
    BizAgent agent = agentRegistry.getAgent(agentId)
        .orElseGet(() -> agentRegistry.getDefaultAgent().orElse(null));

    try {
        String response = agent.process(info, msg);
        if (response == null) {
            fallbackToLlm(msg, info);   // Agent 无法处理，降级
        }
    } catch (Exception e) {
        fallbackToLlm(msg, info);       // 异常降级
    }
}
```

**当前的局限性**：隐式意图切换目前没有自动重新绑定，依赖 Agent 自我判断或降级 LLM 兜底。这是一个已知的待优化点，后续可以通过"意图漂移检测"来改进——当已绑定 Agent 持续无法处理时，重新触发意图识别。

### 6.3 三种绑定状态的对比

| 状态 | 判定条件 | 是否重新识别 | 路由行为 |
|------|---------|------------|---------|
| **未绑定** | 无 session 文件 | ✅ 是 | 完整走意图识别 → 路由 → 绑定 |
| **已绑定（有效期内）** | boundAgent 存在 && expiresAt > now | ❌ 否 | 直接路由到绑定的 Agent |
| **已绑定（已过期）** | expiresAt < now | ✅ 是 | 重新完整路由 |

## 七、响应回写：路由的最后一公里

Agent 处理完消息后，响应通过事件总线回写：

```java
@Async
@EventListener
public void onMessageResponse(MessageResponseEvent event) {
    var channel = channelRegistry.getChannel(event.getChannel());
    if (channel == null) {
        log.error("找不到对应的通道：{}", event.getChannel());
        return;
    }
    channel.responseToUser(event.getResponseMessage());
}
```

**为什么这里还需要 ChannelRegistry？**

```
MsgRouter 不直接依赖任何具体的 Channel 实现
  → 通过 ChannelRegistry.getChannel(channelName) 找到通道
  → 通过 Channel.responseToUser() 发送响应

解耦效果：
  - 消息路由层不需要知道微信/钉钉/飞书的差异
  - 新增通道时，路由层零改动
```

## 八、常见问题

### 8.1 关键词匹配和 LLM 匹配结果冲突怎么办？

**不会冲突**。关键词匹配是"先到先得"——0.9 以上的高置信度直接返回，不会继续走 LLM。只有关键词匹配得分低于 0.7 时才会降级到 LLM。

### 8.2 会话绑定的过期时间多长合适？

目前默认 6 小时。这个时间基于"一次求职会话"的典型时长：
- 太短（如 30 分钟）：用户吃个饭回来就要重新识别
- 太长（如 24 小时）：用户切换话题后仍绑定旧 Agent

### 8.3 群聊中怎么处理身份采集？

群聊中不触发身份采集（`!msg.isGroupTalk()` 判断），因为群聊中的用户身份需要差异化处理。群聊用户的功能受限于 Scope 权限模型。

### 8.4 MsgRouter 的 @Async 会导致并发问题吗？

不会。每个用户的消息隔离在各自的 `UserConversationInfo` 和 `FileSystemSessionAgentBinder` 中，文件锁保证同一会话的串行化访问。

## 九、小结

消息路由是求职派"多 Agent 运行时"的交通枢纽。其核心设计可概括为：

1. **三层意图识别**：系统命令 L0 → 关键词 L1（快路径，低成本）→ LLM L2（慢路径，兜底），在速度和准确性之间取得平衡
2. **置信度驱动的决策**：`IntentClassificationRes.confidence` 控制是否降级，避免不必要的 LLM 调用
3. **会话绑定保证状态一致性**：`SessionAgentBinder` 通过文件持久化 + 6h TTL，保证多轮对话不串台、重启不丢失
4. **路由 + 降级双保险**：`AgentRouter` 找不到合适的 Agent 时，兜底到默认 Agent；Agent 执行失败时，降级到 LLM
