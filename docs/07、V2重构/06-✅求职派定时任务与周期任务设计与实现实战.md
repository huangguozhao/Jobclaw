# ✅求职派定时任务与周期任务设计与实现实战

> 任务调度是 Agent 运行时"多任务"能力的基础设施。从一次性提醒到周期性校招信息推送，背后都需要一个灵活、可靠、用户隔离的任务系统。本文完整记录求职派基于 JobRunr 的任务调度体系的设计思路与实现细节。

---

## 一、为什么需要任务调度系统？

### 1.1 V1 的缺失

在 V1 版本中，求职派完全没有任务调度的概念：

```
用户："明天早上 9 点提醒我面试"
Agent 回复："好的，已设置提醒"     ← 但实际上并没有设置定时任务
                                   ← 第二天不会收到任何提醒
```

**致命问题**：
- **无定时执行**：无法在指定时间执行任务
- **无周期执行**：无法定时抓取校招信息、日报推送
- **无用户隔离**：任务无法关联特定用户
- **无 AI 驱动**：AI Agent 只能"口头答应"，不能真正编排任务

### 1.2 V2 的设计目标

我们提出三个核心诉求：

> **1. Agent 如何创建/调度任务？**
> AI Agent 通过 `TaskTool` 向用户提供任务管理能力，用户说"提醒我 X"，Agent 就能真正创建一个定时任务。

> **2. 任务到期后如何执行？**
> 后台调度器在指定时间触发任务处理，通过 LLM 驱动执行，并向用户推送结果。

> **3. 一次性任务与周期性任务如何统一管理？**
> 一次性任务（定时提醒、延时执行）和周期性任务（Cron 周期触发）共享同一套存储、同一种执行模型，按用户 ID 隔离。

## 二、任务调度架构总览：从问题到方案

### 2.1 架构推演：任务系统面临的核心挑战

在动手设计之前，我们先问自己三个问题：

> **问题 1：谁来发起任务？**
> 是后台管理员配置，还是在 IM 聊天中对 Agent 说一句话就创建？

**直觉方案**：给 Agent 一套工具（Tool），让它通过自然语言交互来创建任务。

```
用户："每天早上 8 点推送校招信息"
  ↓  LLM 理解意图
Agent："好的，老板！"          ← 口头答应，但没有真正执行
```

**问题**：Agent 只能回复文本，没有能力真正编排后台任务。需要一套 Tool 来连接 Agent 和调度器。

**答案**：`TaskTool` —— 把任务操作封装成 Spring AI `@Tool`，让 LLM 用自然语言驱动。

---

> **问题 2：谁在什么时间执行？**
> 任务到期后，谁来执行它？在哪个进程里执行？

**直觉方案**：在业务代码中直接 `Thread.sleep()` + `while(true)` 轮询。

```java
// 反例：手动轮询
while (true) {
    for (Task task : getAllTodoTasks()) {
        if (task.getCreatedAt().isBefore(Instant.now())) {
            execute(task);  // ← 单线程阻塞，任务多了就卡死
        }
    }
    Thread.sleep(1000);  // ← 定时精度差，重启后丢失
}
```

**问题**：
- 应用重启后未执行的任务全部丢失
- 没有分布式协调，多实例部署会重复执行
- 不支持 Cron 表达式，无法实现"每天早上 8 点"

**答案**：引入 **JobRunr** —— 一个内嵌式 Java 任务调度库，支持持久化、重试、分布式锁、Cron 表达式。用它替代手写调度。

---

> **问题 3：执行结果怎么告诉用户？**
> 任务在后台默默执行完了，用户怎么知道结果？

**直觉方案**：把结果写进数据库，用户自己来查。

```java
taskRepository.save(task.withStatus(Status.completed)
        .withFeedback("已完成"));
// (用户不知道，除非主动查询)
```

**问题**：任务调度是"主动推送"场景——系统应该主动告诉用户，而不是等用户来问。

**答案**：通过 `ChannelEventPublisher` 主动推送到用户的 IM 通道（微信/钉钉/飞书），利用心跳机制找到用户活跃的通道。

---

### 2.2 从三个问题到四层架构

把上述思考对应到架构分层：

```
三个问题                         四层架构
─────────                       ────────
问题 1 "谁来发起任务"      →  Agent 层（TaskTool + TaskBizAgent）
                                 AI Agent 通过 Tool 创建/调度任务

问题 2 "谁在什么时间执行"  →  调度管理层（TaskManager）
                                 JobRunr 负责时间触发、排队、重试
                              + 执行层（TaskHandler）
                                 LLM 驱动任务内容执行

问题 3 "结果怎么告诉用户"  →  事件总线 & 渠道层
                                 ChannelEventPublisher 主动推送

不直接属于上述问题但必须有的 →  存储层（TaskRepository）
                                 任务持久化，重启不丢失
```

每一层的职责和边界：

| 层 | 核心类 | 职责 | 不负责什么 |
|---|--------|------|-----------|
| **Agent 层** | `TaskTool`, `TaskBizAgent` | 通过 Tool 暴露任务能力给 LLM | 不负责调度时间、不负责执行逻辑 |
| **调度管理层** | `TaskManager` | 封装 JobRunr，处理入队/定时/周期 | 不负责任务内容执行、不负责存储 |
| **执行层** | `TaskHandler`, `RecurringTaskHandler` | 任务到期后真正干活 | 不负责时间调度、不负责用户通知 |
| **存储层** | `TaskRepository`, `FileSystemTaskRepository` | 任务持久化 | 不负责调度、不负责执行 |
| **事件总线 & 渠道层** | `ChannelEventPublisher` | 主动推送结果给用户 | 不负责任务本身 |

### 2.3 最终架构

```
┌────────────────────────────────────────────────────────────┐
│                   Agent 层（工具调用）                         │
│     TaskTool（@Tool）← TaskBizAgent 注册给 LLM 使用           │
│     【职责】让 LLM 通过自然语言创建/调度/管理任务              │
├────────────────────────────────────────────────────────────┤
│               任务调度管理层 (core/tasks/)                     │
│     TaskManager（JobRunr 调度器封装）                        │
│     ├─ create()          一次性任务，立即入队                │
│     ├─ schedule()        延时任务，指定时间执行              │
│     └─ scheduleRecurrently()  周期性任务，Cron 表达式       │
│     【职责】封装调度细节，提供统一 API                         │
├────────────────────────────────────────────────────────────┤
│               任务执行层 (core/tasks/)                        │
│     TaskHandler              一次性/延时任务执行 + AI 驱动    │
│     RecurringTaskHandler     周期性任务触发 → 生成子任务      │
│     【职责】任务到期后的实际执行逻辑                           │
├────────────────────────────────────────────────────────────┤
│               任务存储层 (core/tasks/)                        │
│     TaskRepository（接口）                                   │
│         └─ FileSystemTaskRepository（YAML/MD 文件实现）      │
│     【职责】任务持久化，重启不丢失                             │
├────────────────────────────────────────────────────────────┤
│              事件总线 & 渠道层                                │
│     ChannelEventPublisher → 主动推送结果给用户                │
│     【职责】通过心跳机制推送到微信/钉钉/飞书                   │
└────────────────────────────────────────────────────────────┘
```

### 2.4 三种任务类型

| 任务类型 | 触发方式 | 典型场景 |
|---------|---------|---------|
| **一次性任务** | 立即入队，尽快执行 | 用户说"帮我查一下秋招时间表" |
| **延时任务** | 指定时间点执行 | "明天早上 9 点提醒我面试" |
| **周期性任务** | Cron 表达式周期触发 | "每天早上 8 点推送今日校招信息" |

### 2.5 核心链路

```
用户（通过 IM）："每天早上 8 点帮我推送校招信息"
  │
  ▼
TaskBizAgent.process/stream()
  │  LLM 识别意图 → 调用 TaskTool.scheduleRecurringTask()
  ▼
TaskManager.scheduleRecurrently(cron="0 8 * * *", ...)
  │  1. 保存 RecurringTask 到文件系统
  │  2. 注册 JobRunr 周期性 Job
  ▼
JobRunr 调度器 ──→ RecurringTaskHandler.executeTask()
  │                     │  (每天早上 8 点触发)
  │                     ▼
  │               TaskManager.createTaskFromRecurringTask()
  │                     │  生成一次性的 Task 并入队
  │                     ▼
  │               TaskHandler.executeTask()
  │                     │  LLM 驱动执行 → 校招信息采集 + 推送
  │                     ▼
  │               ChannelEventPublisher.publishProactiveMessage()
  │                     │  通过心跳机制推送到用户 IM
  │                     ▼
  │               用户收到："今日校招信息已更新..."
  ▼
（每天重复）
```

## 三、核心抽象设计

在设计任务模型之前，需要想清楚几个根本问题：

### 3.1 Task 模型：从"一条记录"到"完整抽象"

#### 设计起点：任务最少需要哪些信息？

**直觉方案**：一条简单的数据库记录，记下"谁要在什么时候做什么事"。

```java
// 反例：过于简化的任务记录
public class Task {
    private String name;
    private String description;
    private String userId;
    private LocalDateTime executeAt;
}
```

**问题**：

| 缺失了什么 | 导致的问题 |
|-----------|-----------|
| 没有 ID | 无法在系统中唯一引用这个任务 |
| 没有状态 | 任务是待执行、执行中还是已完成？无法追踪 |
| 没有创建时间 | 不知道任务是什么时候创建的 |
| 没有用户隔离 | 谁的任务？没有强制校验 |
| 可变对象 | 并发修改时状态不一致怎么办？ |

#### 第一步：补充核心字段

从上述缺陷反推，一个任务至少需要：

| 字段 | 用途 | 为什么必须 |
|------|------|-----------|
| `id` | 全局唯一标识 | 被调度器、执行器、存储层引用 |
| `name` | 任务名称 | 人类可读，LLM 管理时使用 |
| `createdAt` | 创建时间 | 记录何时创建，用于日期目录存储 |
| `status` | 当前状态 | 任务生命周期追踪 |
| `description` | 详细描述 | LLM 执行时的 Prompt 内容 |
| `jobClawUserId` | 所属用户 | 用户隔离的基石 |

#### 第二步：用状态机替代"待执行标记"

**直觉方案**：一个布尔字段 `done` 标记是否完成。

```java
// 反例：布尔状态
private boolean done;       // true=已完成, false=待处理
```

**问题**：
- 无法区分"等待执行"和"正在执行"
- 无法表达"等待用户输入"的中间态
- 如果执行失败，需要重试，但布尔值无法表达"回退"

**解决方案**：四态枚举

```java
public enum Status {
    todo,                    // 待执行（初始态）
    in_progress,             // 执行中（防止重复触发）
    completed,               // 已完成（正常终态）
    awaiting_human_input     // 等待用户输入（中间态，需要用户确认后继续）
}
```

**生命周期**：

```
todo ──→ in_progress ──→ completed
                  │
                  └──→ awaiting_human_input ──→（用户回复后重新 todo）
                  
如果执行异常：in_progress ──→ todo（回滚，允许重试）
```

#### 第三步：不可变设计解决并发问题

当 `TaskHandler` 和 `TaskManager` 可能同时访问同一个任务时：

```java
// 反例：可变对象并发问题
task.setStatus(Status.in_progress);
// ↓ 此时另一个线程把 status 改成了 completed
task.setFeedback("执行完毕");  // ← 状态已被覆盖
```

**为什么不可变对象能解决这个问题？**

```java
public Task withStatus(Status newStatus) {
    return new Task(id, name, createdAt, newStatus, description, jobClawUserId);
    // ↑ 返回新对象，原对象不变
}
```

**使用方式**：

```java
Task inProgress = taskRepository.save(task.withStatus(Status.in_progress));
// ↑ task 仍然是 todo，inProgress 是新对象
// 两个线程各自持有自己的副本，互不干扰
```

#### 最终设计

```java
@Getter
public class Task {

    public enum Status {
        todo, in_progress, completed, awaiting_human_input
    }

    private final String id;
    private final String name;
    private final Instant createdAt;
    private final Status status;
    private final String description;
    private final String jobClawUserId;   // ← 用户隔离的关键

    /**
     * 创建立即执行的任务
     * 【强制要求】必须传入 jobClawUserId
     */
    public static Task newTask(String name, String description, String jobClawUserId) {
        if (jobClawUserId == null || jobClawUserId.isEmpty()) {
            throw new IllegalArgumentException("jobClawUserId is required");
        }
        return new Task(null, name, Instant.now(), Status.todo, description, jobClawUserId);
    }

    /**
     * 创建指定时间执行的任务
     */
    public static Task newTask(String name, Instant createdAt, String description, String jobClawUserId) {
        return new Task(null, name, createdAt, Status.todo, description, jobClawUserId);
    }

    /**
     * 状态转换：生成新对象（不可变设计）
     */
    public Task withStatus(Status newStatus) { ... }

    /**
     * 添加 AI 执行反馈
     */
    public Task withFeedback(String feedback) { ... }
}
```

### 3.2 RecurringTask 模型：为什么和 Task 分开？

#### 设计起点：周期性任务也是"任务"，为什么不复用同一个模型？

**直觉方案**：给 Task 加一个 `cronExpression` 字段，有值就是周期性任务。

```java
// 反例：用同一模型表示周期任务
public class Task {
    private String name;
    private String cronExpression;  // null=一次性, 有值=周期性
    private Status status;          // ← 周期性任务需要状态吗？
}
```

**问题**：

```
场景：每天早上 8 点推送校招信息
  ↓
第一次 Cron 触发 → Task 状态变为 in_progress → 执行完毕 → completed
  ↓
第二次 Cron 触发 → 但状态是 completed，无法再执行！
```

**核心矛盾**：一次性任务关注"这一次的执行"，周期性任务描述的是**规则**，本身没有执行状态。

#### 对比分析

| 维度 | 一次性任务（Task） | 周期性任务（RecurringTask） |
|------|------------------|--------------------------|
| **本质** | 一次执行单元 | 调度规则 |
| **有状态吗？** | 有（todo/in_progress/completed） | 无（只有配置信息） |
| **如何执行？** | TaskHandler 直接执行 | 触发时生成一个一次性 Task |
| **生命周期** | 创建 → 执行 → 完成/失败 | 创建 → 每天触发 → 手动删除 |
| **Cron 表达式** | 无 | 有 |

**设计决策**：分成两个模型，各司其职。

```java
@Getter
public class RecurringTask {

    private final String id;
    private final String name;
    private final String description;
    private final String jobClawUserId;
    private final String cronExpression;     // Cron 表达式，如 "0 8 * * *"

    public static RecurringTask newRecurringTask(String name, String description,
                                                  String jobClawUserId, String cronExpression) {
        if (jobClawUserId == null || jobClawUserId.isEmpty()) {
            throw new IllegalArgumentException("jobClawUserId is required");
        }
        if (cronExpression == null || cronExpression.isEmpty()) {
            throw new IllegalArgumentException("cronExpression is required");
        }
        return new RecurringTask(null, name, description, jobClawUserId, cronExpression);
    }
}
```

**周期性任务的工作方式**：

```
RecurringTask（规则）
  │  cronExpression = "0 8 * * *"
  │
  ├── 第1天 08:00 → 生成 Task#1（状态 todo）→ 执行 → completed
  ├── 第2天 08:00 → 生成 Task#2（状态 todo）→ 执行 → completed
  ├── 第3天 08:00 → 生成 Task#3（状态 todo）→ 执行 → completed
  └── ...
```

RecurringTask 本身没有状态变化，它只是定时"产卵"——每次 Cron 触发时生成一个全新的一次性 Task。

### 3.3 TaskRepository 接口：为什么一定要接口抽象？

#### 设计起点：最简单的方案——直接写文件

**直觉方案**：在 TaskManager 里直接读写文件。

```java
// 反例：TaskManager 直接读写文件
@Component
public class TaskManager {
    public void create(String name, String desc, String userId) {
        // 1. 构造 Task
        Task task = new Task(...);
        // 2. 直接写文件
        Files.writeString(path, serialize(task));
        // 3. 入队
        jobScheduler.enqueue(() -> executeTask(task.getId()));
    }
}
```

**问题**：

```
如果将来要切换到数据库？

方案 A：在 TaskManager 里加 if-else
  if (storageType.equals("file")) {
      // 写文件
  } else if (storageType.equals("jpa")) {
      // 写数据库
  }
  ← 每个方法都要加，TaskManager 越来越臃肿

方案 B：抽象接口
  TaskRepository.save(task)
  ← 文件实现和 JPA 实现各写各的，TaskManager 不用改
```

**设计决策**：接口隔离。

```java
public interface TaskRepository {

    // ---- 一次性任务 ----
    Task save(Task task);
    Task getTaskById(String id);
    List<Task> getTasksByUser(LocalDate date, Task.Status status, String jobClawUserId);

    // ---- 周期性任务 ----
    RecurringTask save(RecurringTask recurringTask);
    RecurringTask getRecurringTaskById(String id);
    List<RecurringTask> getAllRecurringTasks();
    List<RecurringTask> getRecurringTasksByUser(String jobClawUserId);
    void deleteRecurringTask(String id);
}
```

**接口抽象的价值**：

| 角色 | 关心什么 | 不关心什么 |
|------|---------|-----------|
| `TaskManager` | 调度（入队/定时/周期） | 任务存哪里、什么格式 |
| `FileSystemTaskRepository` | 文件读写、目录结构 | 任务什么时候执行 |
| `JpaTaskRepository`（将来） | JPA 实体、数据库事务 | 任务什么时候执行 |

**依赖方向**：

```
TaskManager → TaskRepository（接口） ← FileSystemTaskRepository
                                    ← JpaTaskRepository（将来）
```

TaskManager 只依赖接口，不依赖具体实现。替换存储实现时，TaskManager 一行代码都不用改。

## 四、FileSystemTaskRepository：文件系统存储实现

### 4.1 存储结构推演：文件该怎么放？

#### 设计起点：所有任务平铺在一个目录里

**直觉方案**：像日志文件一样，所有任务 `.md` 文件放在一个目录。

```
workspace/tasks/
├── meeting_reminder.md
├── interview_prep.md
├── daily_job_push.md
├── weekly_report.md
├── ...   ← 几天后几百个文件混在一起
```

**问题**：

```
用户 A 想看自己今天有哪些任务？
  → 遍历所有文件，逐个解析 frontmatter，筛选 jobClawUserId + createdAt
  → 文件越多越慢，O(n) 复杂度

用户 B 想删除自己的周期任务？
  → 同样要遍历所有文件
  → 万一文件名冲突（两个用户都叫 "reminder"）？
```

#### 第一步：按用户分目录

```
workspace/tasks/
├── user-1001/
│   ├── meeting_reminder.md
│   └── interview_prep.md
├── user-1002/
│   ├── reminder.md
│   └── daily_push.md
```

**解决了**：按用户查询时直接定位到子目录，不再全量遍历。

**还存在的问题**：

```
用户 1001 有 1000 个任务 → user-1001/ 下 1000 个文件
用户 A："查一下我今天有哪些任务"
  → 遍历 1000 个文件，逐个解析 frontmatter 看 createdAt
  → 仍然慢
```

#### 第二步：按日期分目录

```
workspace/tasks/
├── user-1001/
│   ├── 2026-04-20/
│   │   ├── 090000-meeting_reminder.md
│   │   └── 140000-interview_prep.md
│   ├── 2026-04-21/
│   │   └── 100000-follow_up.md
│   └── recurring/
│       ├── daily_job_push.md
│       └── weekly_report.md
└── user-1002/
    └── ...
```

**解决了**：用户查"今天"的任务 → 直接进入今天的目录 → 只读几个文件。

**文件命名规则**：

```
一次性任务：workspace/tasks/{userId}/{yyyy-MM-dd}/{HHmmss}-{sanitized_name}.md
周期性任务：workspace/tasks/{userId}/recurring/{sanitized_name}.md
```

**为什么一次性任务按时间命名，周期性任务按名称命名？**

| 任务类型 | 查询模式 | 命名策略 |
|---------|---------|---------|
| 一次性任务 | 按日期查询 | 时间戳前缀，同一天的文件按时间排序 |
| 周期性任务 | 按名称查询/删除 | 直接使用任务名，方便查找和删除 |

### 4.2 文件格式选择：为什么用 YAML Frontmatter？

#### 设计起点：把任务信息存成 JSON 文件

```json
{
  "task": "meeting_reminder",
  "createdAt": "2026-04-20T09:00:00Z",
  "status": "completed",
  "description": "提醒用户参加 10 点的面试",
  "jobClawUserId": "1001"
}
```

**问题**：

```
开发者想调试：
  打开文件 → {"task":"meeting_reminder","createdAt":"...",...}
  ← JSON 可读性还行，但无法直接在里面写注释或笔记

想用手工创建一个任务试试：
  要写合法的 JSON，少个逗号就解析失败
  ← 不够"开发者友好"
```

**对比方案**：

| 格式 | 可读性 | 手工创建 | 解析复杂度 | 元数据分离 |
|------|--------|---------|-----------|-----------|
| JSON | 一般 | 严格 | 低 | 否 |
| YAML | 好 | 宽松 | 低 | 否 |
| **YAML Frontmatter** | **最好** | **宽松** | **低** | **是（内容可自由扩展）** |

**YAML Frontmatter 的特点**：`---` 之间的内容是结构化元数据，`---` 之后可以放任意内容（如 AI 执行日志、备注等）。

**一次性任务文件**：

```yaml
---
task: meeting_reminder
createdAt: 2026-04-20T09:00:00Z
status: completed
description: 提醒用户参加 10 点的面试
jobClawUserId: 1001
---
（这里将来可以放 AI 执行的详细日志）
```

**周期性任务文件**：

```yaml
---
task: daily_job_push
description: 每天早上 8 点推送今日校招信息
jobClawUserId: 1001
cronExpression: 0 8 * * *
---
```

### 4.3 为什么选择文件存储？

| 维度 | 文件存储 | 数据库存储 |
|------|---------|-----------|
| **依赖** | 零依赖 | 需要 MySQL/PostgreSQL |
| **部署** | 拷贝即可 | 需要建表、配置数据源 |
| **可读性** | 直接打开查看 | 需要 SQL 查询 |
| **查询能力** | 有限 | 灵活 |
| **推荐场景** | 开发/单机部署 | 生产集群部署 |

**选择的逻辑**：

```
项目阶段 → 开发初期，快速验证
需求规模 → 单机部署，几千个任务
团队能力 → 不希望为了任务存储引入数据库依赖

→ 文件系统 + YAML Frontmatter 是最轻量的选择
→ 将来需要时，新增 JpaTaskRepository 即可迁移
```

### 4.4 关键实现细节

**1. Task 的 ID 即文件路径**

```java
@Override
public Task save(Task task) {
    Path path = ofNullable(task.getId())
            .map(Path::of)           // 已有 ID → 覆盖写入
            .orElseGet(() -> buildTaskPath(task));  // 新任务 → 构建路径
    writeTaskFile(path, task);
    return new Task(path.toAbsolutePath().toString(), ...);  // ID = 绝对路径
}
```

**为什么不用 UUID？**

```
方案 A：UUID 作为 ID
  task-uuid-123e4567-e89b-12d3-a456-426614174000
  ← 全局唯一，但没有任何业务含义

方案 B：文件路径作为 ID
  D:/workspace/tasks/1001/2026-04-20/090000-meeting_reminder.md
  ← 全局唯一，且包含用户、日期、任务名信息

  读取时：直接 path = Path.of(id); Files.readString(path);
  ← 不需要查索引，不需要映射表
```

**2. 名称安全化**

```java
static String sanitizeName(String name) {
    return name
            .replaceAll("[^a-zA-Z0-9._-]", "_")   // 非法字符替换为 _
            .replaceAll("_{2,}", "_");             // 连续 _ 合并
}
```

**为什么需要 sanitize？**

```
Agent 创建的任务名举例：
  "提醒: 明天面试"       → "提醒__明天面试"（: 被替换）
  "帮我查一下/秋招信息"  → "帮我查一下_秋招信息"（/ 被替换）
  "task   name"         → "task_name"（连续空格合并）

如果不 sanitize：
  Windows 不允许文件名包含 : / \ < > " | ? *
  跨平台部署时直接报错
```

**3. 日期目录化查询**

```java
@Override
public List<Task> getTasksByUser(LocalDate date, Task.Status status, String jobClawUserId) {
    Path dir = taskDir.resolve(jobClawUserId)
                      .resolve(date.format(DateTimeFormatter.ofPattern("yyyy-MM-dd")));
    if (!Files.exists(dir)) return List.of();
    try (Stream<Path> files = Files.list(dir)) {
        return files
                .filter(p -> p.getFileName().toString().endsWith(".md"))
                .map(p -> getTaskById(p.toAbsolutePath().toString()))
                .filter(t -> (status == null || t.getStatus() == status))
                .toList();
    }
}
```

**设计逻辑**：

```
查询"用户 1001 在 2026-04-20 的待办任务"
  ↓
1. 定位目录：workspace/tasks/1001/2026-04-20/  ← O(1)
2. 列出文件：只有当天的任务文件  ← 少量文件
3. 解析并过滤：逐个解析 frontmatter + 按 status 过滤
  ↓
不需要索引，不需要 SQL，目录结构本身就是索引
```

## 五、TaskManager：调度管理器

### 5.1 为什么需要 TaskManager？

#### 设计起点：直接在业务代码中调用 JobRunr

**直觉方案**：谁需要调度任务，谁就直接注入 `JobScheduler`。

```java
// 反例：散落在各处的调度调用
@Service
public class SomeService {
    @Autowired
    private JobScheduler jobScheduler;

    public void remindUser(...) {
        jobScheduler.schedule(executionTime, 
            () -> taskHandler.executeTask(taskId));  // ← 直接调用 JobRunr
    }
}

@Service
public class AnotherService {
    @Autowired
    private JobScheduler jobScheduler;

    public void pushDaily() {
        jobScheduler.scheduleRecurrently(cron, 
            () -> recurringHandler.executeTask(id));  // ← 又在直接调
    }
}
```

**问题**：

| 问题 | 后果 |
|------|------|
| **耦合 JobRunr** | 所有使用调度的代码都依赖 JobRunr，换调度库要改所有地方 |
| **代码重复** | 每个调用者都要写：保存 Task → 入队 → 日志，到处重复 |
| **容易遗漏** | 有人直接入队但忘记保存 Task，任务执行时找不到记录 |
| **不易测试** | 直接调用 JobRunr 的代码不方便 mock |

**解决方案**：`TaskManager` —— 封装 JobRunr，提供统一的调度 API。

```java
@Component
public class TaskManager {
    private final JobScheduler jobScheduler;
    private final StorageProvider storageProvider;
    private final TaskRepository taskRepository;
}
```

**封装后**：

```java
// 调用者只需关心"我要创建一个任务"
taskManager.create(name, description, userId);
// 不需要知道 JobRunr，不需要自己保存 Task
```

### 5.2 三种调度方式的推演

**场景 1：用户说"帮我查一下秋招时间表"**

这是最常见的场景——用户提出一个请求，系统立即执行。

```
用户 → Agent → TaskTool.createTask() → TaskManager.create()
  ↓
保存 Task → jobScheduler.enqueue() → JobRunr 后台线程立即执行
```

```java
public void create(String name, String description, String jobClawUserId) {
    Task task = taskRepository.save(Task.newTask(name, description, jobClawUserId));
    jobScheduler.<TaskHandler>enqueue(x -> x.executeTask(task.getId()));
    log.info("Task '{}' ({}) has been created for user {}.", task.getName(), task.getId(), jobClawUserId);
}
```

**为什么 create 是"入队"而不是"直接执行"？**

```
方案 A：直接在当前线程执行
  taskHandler.executeTask(task);
  ← 如果任务耗时 30 秒，用户要等 30 秒才能收到 Agent 的其他回复

方案 B：入队后台执行（求职派的方案）
  jobScheduler.enqueue(() -> taskHandler.executeTask(task.getId()));
  ← Agent 立即回复"已为您创建任务"，后台慢慢执行
  ← 执行完成后通过 ChannelEventPublisher 主动推送结果
```

---

**场景 2：用户说"明天早上 9 点提醒我面试"**

需要指定时间执行，核心挑战是**时区处理**。

```java
public void schedule(LocalDateTime executionTime, String name,
                     String description, String jobClawUserId) {
    // LocalDateTime → Instant（系统默认时区）
    Instant createdAt = executionTime.atZone(ZoneId.systemDefault()).toInstant();
    Task task = taskRepository.save(Task.newTask(name, createdAt, description, jobClawUserId));
    jobScheduler.<TaskHandler>schedule(executionTime, x -> x.executeTask(task.getId()));
    log.info("Task '{}' ({}) has been scheduled at {} for user {}.",
            task.getName(), task.getId(), executionTime, jobClawUserId);
}
```

**时区处理的细节**：

```
用户（北京时间，UTC+8）："明天早上 9 点提醒我"
  ↓
Agent 计算：LocalDateTime.now().plusDays(1).withHour(9)
  → 2026-04-21T09:00:00（无时区信息）
  ↓
JobRunr.schedule(2026-04-21T09:00:00)  → 在北京时间 09:00 执行 ✓
  ↓
持久化 Task 时：
  executionTime.atZone(ZoneId.systemDefault()).toInstant()
  → 2026-04-21T01:00:00Z（UTC 时间）
  ↓
如果将来有时区转换需求，Instant 是绝对的，不会因为时区变化而误解
```

**场景 3：用户说"每天早上 8 点推送校招信息"**

这是周期性任务的典型场景——需要 Cron 表达式持续触发。

```java
public void scheduleRecurrently(String cronExpression, String name,
                                 String description, String jobClawUserId) {
    RecurringTask recurringTask = taskRepository.save(
            RecurringTask.newRecurringTask(name, description, jobClawUserId, cronExpression));
    jobScheduler.<RecurringTaskHandler>scheduleRecurrently(
```

### 5.3 周期性任务管理：从规则到执行的转换

**周期性任务的特殊性**：

周期性任务本身不直接执行，它每次触发时**生成一个一次性任务**：

```
JobRunr Cron 触发
  │
  ▼
RecurringTaskHandler.executeTask(recurringTaskId)
  │  1. 从文件系统加载 RecurringTask
  │  2. 创建一次性 Task（name/description 相同）
  │  3. 入队执行
  ▼
TaskHandler.executeTask(taskId)   ← 标准的任务执行流程
```

**为什么需要"周期任务 → 一次性任务"的转换？**

```
方案 A：周期任务直接执行
  RecurringTaskHandler.executeTask()
    → LLM 调用采集信息
    → 推送消息
  问题：如果执行失败，重试怎么处理？执行日志在哪里？

方案 B：周期任务生成子任务（求职派的方案）
  RecurringTaskHandler.executeTask()
    → TaskManager.createTaskFromRecurringTask()
      → TaskHandler.executeTask()  ← 完整的执行链路
  优点：共享一次性任务的重试、状态追踪、失败处理机制
```

**createTaskFromRecurringTask 的实现**：

```java
public void createTaskFromRecurringTask(RecurringTask recurringTask) {
    Task task = taskRepository.save(Task.newTask(
            recurringTask.getName(),
            recurringTask.getDescription(),
            recurringTask.getJobClawUserId()));
    jobScheduler.<TaskHandler>enqueue(x -> x.executeTask(task.getId()));
}
```

**删除周期性任务**：

```java
public void deleteRecurringTask(String name, String jobClawUserId) {
    // 1. 查找用户的周期性任务
    RecurringTask task = taskRepository.getRecurringTasksByUser(jobClawUserId)
            .stream().filter(x -> x.getName().equals(name)).findFirst().orElseThrow();

    // 2. 删除 JobRunr 的周期性 Job
    jobScheduler.deleteRecurringJob(task.getName());

    // 3. 删除已调度但未执行的 Job 实例
    List<Job> jobList = storageProvider.getJobList(StateName.SCHEDULED, ...);
    jobList.stream()
            .filter(j -> j.getRecurringJobId().map(task.getName()::equals).orElse(false))
            .map(Job::getId).findFirst()
            .ifPresent(jobScheduler::delete);

    // 4. 删除文件系统中的周期性任务记录
    taskRepository.deleteRecurringTask(task.getId());
}
```

**为什么删除需要四步？**

```
用户："取消每天早上 8 点的推送"
  ↓
直觉：把文件删了就行
  ↓
问题：JobRunr 的内存中还有这个周期性 Job 的引用，
      下次 Cron 触发时还是会执行（虽然文件已经没了）
      而且可能已经有一个明天的执行在队列里排队了
```

| 步骤 | 删除的目标 | 为什么不能省略 |
|------|-----------|--------------|
| 1 | 文件系统中的 RecurringTask 记录 | 防止系统重启后重新注册 |
| 2 | JobRunr 的 Recurring Job | 停止后续触发 |
| 3 | 已调度但未执行的 Job 实例 | 取消已排队的下一次执行 |
| 4 | 文件系统中的记录（重复） | 清理持久化数据 |

**删除的四步缺一不可**：只删文件 → JobRunr 还会触发；只删 Job → 重启后又从文件恢复了。

## 六、任务执行引擎

### 6.1 TaskHandler：一次性任务执行

`TaskHandler` 是任务执行的**核心引擎**，它负责：

1. 加载任务，校验状态
2. 调用 LLM 执行任务
3. 更新任务状态
4. 通知用户结果

```java
@Component
public class TaskHandler {

    private final LlmCaller llmCaller;
    private final TaskRepository taskRepository;
    private final ChannelEventPublisher channelEventPublisher;

    @Job(name = "%0", retries = 3)     // ← JobRunr 注解：支持自动重试
    public void executeTask(String taskId) {
        Task task = taskRepository.getTaskById(taskId);

        // 状态校验：只有 todo 状态才能执行
        if (!Task.Status.todo.equals(task.getStatus())) {
            throw new IllegalStateException("Cannot handle task '" + task.getName()
                    + "' with status " + task.getStatus());
        }

        Task inProgress = taskRepository.save(task.withStatus(Task.Status.in_progress));
        try {
            // 构建 AI 提示词，让 LLM 执行任务
            String agentInput = formatTaskForAgent(inProgress);
            var result = llmCaller.call(
                    new UserConversationInfo(task.getJobClawUserId(), null, task.getId(), false),
                    new Prompt(agentInput),
                    TaskResult.class);

            // 更新任务状态 + 用户通知
            taskRepository.save(inProgress.withFeedback(result.feedback())
                    .withStatus(result.newStatus()));
            notifyUser(task, result);

        } catch (Exception e) {
            // 失败回滚：恢复 todo 状态，允许重试
            taskRepository.save(inProgress.withStatus(Task.Status.todo));
            throw e;
        }
    }
}
```

**设计要点**：

| 特性 | 说明 |
|------|------|
| **幂等性** | 只有 `todo` 状态的任务才会执行，避免重复执行 |
| **重试机制** | `@Job(retries = 3)` 注解，JobRunr 自动重试 |
| **状态追踪** | `todo → in_progress → completed/awaiting_human_input` |
| **失败回滚** | 异常时恢复 `todo` 状态，确保可重试 |
| **AI 驱动** | 不是硬编码执行逻辑，而是通过 LLM 动态决策 |

### 6.2 AI 驱动的任务执行

`TaskHandler` 不硬编码任务逻辑，而是通过 LLM 动态执行：

```java
private String formatTaskForAgent(Task task) {
    return String.format("""
            你是一个智能任务助手，需要执行以下任务并返回结果。

            ## 任务信息
            - 任务名称: %s
            - 任务描述: %s

            ## 执行要求
            1. **语言要求**: 必须使用**中文**回复用户
            2. **内容要求**:
               - 如果是提醒类任务，直接告诉用户提醒的内容和时间
               - 如果是查询类任务，返回查询结果摘要
               - 如果是操作类任务，说明已完成的动作
            3. **状态选择**:
               - 任务成功完成 → 返回 'completed'
               - 需要用户确认 → 返回 'awaiting_human_input'
            4. **反馈格式**: 简洁明了，例如：
               - "⏰ 提醒：您有会议将在2分钟后开始"
               - "✅ 已完成：共找到5个匹配岗位"

            ## 返回格式（JSON）
            {
              "newStatus": "completed",
              "feedback": "⏰ 提醒：您的会议将在2分钟后开始"
            }
            """, task.getName(), task.getDescription());
}
```

**为什么是 AI 驱动，而不是硬编码？**

| 场景 | 硬编码方案 | AI 驱动方案 |
|------|-----------|------------|
| 提醒任务 | 固定模板："提醒：xxx 时间到了" | LLM 根据任务描述生成个性化提醒 |
| 查询任务 | 固定查询逻辑，修改需改代码 | LLM 使用工具查询数据，动态组织回复 |
| 复合任务 | 多重 if-else，难以维护 | LLM 自主决策，调用多个工具 |

### 6.3 RecurringTaskHandler：周期性任务触发

周期性任务处理器非常轻量——它的职责是**触发而不是执行**：

```java

        taskManager.createTaskFromRecurringTask(recurringTask);

    }
}
```

**createTaskFromRecurringTask() 的实现**：

```java
public void createTaskFromRecurringTask(RecurringTask recurringTask) {

```

**完整执行链路**：

```

  │  加载周期性任务配置
  │
  ▼
TaskManager.createTaskFromRecurringTask()
  │  创建一次性 Task
  │  入队
  ▼
TaskHandler.executeTask()
  │  LLM 驱动执行
  │  更新状态
  ▼

  │  推送结果到用户 IM
  ▼
用户收到通知
```

```java
        Schedules a task using JobRunr for a specific time in the future.
        Use this when a user explicitly mentions a time or date.
        - delaySeconds: The number of seconds from now when the task should run.
        ...
        """)
public String scheduleTask(
        @JsonPropertyDescription("任务延迟执行的秒数，如 600 表示10分钟后")
        Long delaySeconds,
        @JsonPropertyDescription("任务名，始终是英文格式")
        String name,
        @JsonPropertyDescription("任务的描述，使用中文")
        String description,
        ToolContext toolContext) {
    String jobClawUserId = (String) toolContext.getContext().get("jobClawUserId");
    LocalDateTime executionTime = LocalDateTime.now().plusSeconds(delaySeconds);
    this.taskManager.schedule(executionTime, name, description, jobClawUserId);
    return String.format("Task '%s' has been scheduled to execute in %d seconds.", name, delaySeconds);
}
```

**为什么用 delaySeconds 而不是直接接受时间点？**

```
用户说："10分钟后提醒我"
  ↓
LLM 计算：10分钟 = 600秒
  ↓
Tool 调用：scheduleTask(delaySeconds=600, name="...", description="...")
```

如果直接接受时间点，LLM 需要自己处理时区、日期格式、时间解析等问题，容易出错。`delaySeconds` 是 LLM 最容易计算的相对时间。

### 7.4 scheduleRecurringTask：周期性任务

```java
@Tool(name = "scheduleRecurringTask", description = """
        Schedules a task that repeats at regular intervals based on a cron expression.
        Use this for recurring activities like daily reports, weekly checks, etc.
        - cronExpression: Quartz-style cron expression (e.g., '0 12 * * *' for daily at noon).
        - name: Short, descriptive identifier (e.g., 'weekly-log-cleanup').
        ...
        """)
public String scheduleRecurringTask(
        @JsonPropertyDescription("Cron表达式，如 0 12 * * * 表示每天中午12点")
        String cronExpression,
        @JsonPropertyDescription("任务名，始终是英文格式")
        String name,
        @JsonPropertyDescription("任务的描述，使用中文")
        String description,
        ToolContext toolContext) { ... }
```

### 7.5 用户上下文传递

`TaskTool` 通过 `ToolContext` 获取当前用户信息：

```java
String jobClawUserId = (String) toolContext.getContext().get("jobClawUserId");
```

这个上下文由 `BizAgentLlmCaller` 在构建 ReActAdvisor 时注入：

```java
.toolContext(Map.of(
    "jobClawUserId", user.jobClawUserId(),
    "user", user,
    "msg", msg
))
```

**设计价值**：工具函数无需感知当前用户是谁，通过 ToolContext 透明传递，实现按用户隔离。

## 八、TaskBizAgent：任务 Agent

`TaskBizAgent` 是任务系统的业务 Agent，它负责将任务工具注册给 LLM：

```java
@Component
public class TaskBizAgent extends AbsBizAgent {

    private final TaskManager taskManager;

    @Override
    public ToolCallback[] getTools() {
        return ToolCallbacks.from(
            TaskTool.builder()
                .taskManager(taskManager)
                .build()
        );
    }

    @Override
    public String getSystemPrompt() {
        return """
            You are an interactive assistant working for JobClaw
            helping them with all their tasks and todos.
            Use the skills and the tools available to you to assist the user.
            ...
            """;
    }
}
```

**Agent 注册机制**：
- `@Component` 标记 → Spring 自动扫描
- `AgentRegistry` 自动发现并注册
- `IntentClassifier` 通过意图识别路由到该 Agent
- 用户消息匹配任务意图时，自动绑定到 TaskBizAgent

使用时，用户只需通过 IM 发送：

```
用户："帮我设置一个每天早上 8 点推送校招信息的任务"
  ↓ 意图识别 → TaskBizAgent
  ↓ LLM 调用 → TaskTool.scheduleRecurringTask()
  ↓ TaskManager.scheduleRecurrently()
  ↓ 用户收到："✅ 已创建周期性任务 'daily_job_push'，每天早上 8 点执行"
```

## 九、完整链路与事件流

### 9.1 一次性任务链路

```
用户："帮我查一下今年的秋招时间表"
  │
  ├─ IM 通道接收消息
  ├─ MsgRouter 路由 → TaskBizAgent
  │
  ▼
TaskBizAgent.stream()
  │  LLM 调用 → 执行 TaskTool.createTask()
  ▼
TaskManager.create(name="autumn_recruitment", ...)
  │  1. 保存 Task → workspace/tasks/1001/2026-04-20/143000-autumn_recruitment.md
  │  2. JobRunr.enqueue()
  ▼
TaskHandler.executeTask(taskId)
  │  1. 加载 Task，校验状态
  │  2. 调用 LLM：使用 LlmCaller 执行任务
  │  3. LLM 使用内置工具查询秋招信息
  │  4. 生成结果
  ▼
notifyUser(task, result)
  │  ChannelEventPublisher.publishProactiveMessage()
  ▼
用户收到："✅ 已查询到 2026 年秋招时间表：..."
```

### 9.2 周期性任务链路

```
用户："每天早上 8 点推送校招信息"
  │
  ▼
TaskManager.scheduleRecurrently("0 8 * * *", "daily_job_push", ...)
  │  1. 保存 RecurringTask → workspace/tasks/1001/recurring/daily_job_push.md
  │  2. JobRunr.scheduleRecurrently("daily_job_push", "0 8 * * *")
  ▼
（每天早上 8:00）
  │
  ▼
RecurringTaskHandler.executeTask(recurringTaskId)
  │  TaskManager.createTaskFromRecurringTask()
  ▼
TaskManager.create(name="daily_job_push", ...)
  │  保存一次性 Task → 入队
  ▼
TaskHandler.executeTask(taskId)
  │  LLM 采集校招信息 → 推送结果
  ▼
用户收到："今日校招信息已更新，共 5 个新岗位..."
```

### 9.3 事件驱动的用户通知

任务执行完成后，通过 `ChannelEventPublisher` 主动推送给用户：

```java
private void notifyUser(Task task, TaskResult result) {
    String userId = task.getJobClawUserId();
    var pre = aiUserPreferenceProperties.getUserPreference(userId);
    if (pre != null) {
        for (var channel : pre.getChannels()) {
            var tag = channelEventPublisher.publishProactiveMessage(
                    "TRSP_" + task.getId(),
                    userId,
                    channel,
                    result.feedback());
            if (tag) return;  // 成功推送后停止
        }
    }
}
```

**通知流程**：

```
TaskHandler.notifyUser()
  │
  ▼
ChannelEventPublisher.publishProactiveMessage()
  │  1. 从 ChannelRegistry 获取通道实例
  │  2. 获取心跳适配器构建响应
  │  3. 发布 MessageResponseEvent
  │
  ▼
MsgRouter.onMessageResponse() @Async
  │
  ▼
Channel.responseToUser() → 推送到 IM
```

## 十、扩展指南与常见问题

### 10.1 如何迁移到数据库存储？

只需新增 `JpaTaskRepository` 实现 `TaskRepository` 接口：

```java
@Component
@ConditionalOnProperty(name = "agent.task.storage", havingValue = "jpa")
public class JpaTaskRepository implements TaskRepository {
    // 使用 Spring Data JPA 实现
}
```

现有代码无需改动——`TaskManager` 依赖的是接口，不是实现。

### 10.2 如何实现任务依赖（DAG）？

当前架构不支持任务间的依赖关系。如果需要"任务 A 完成后自动触发任务 B"，可以：

- 在 `TaskHandler` 执行完成后检查任务配置，触发下游任务
- 使用 LangGraph4J 工作流编排
- 在 Task 模型上增加 `dependsOn` 字段

### 10.3 任务超时如何处理？

JobRunr 支持超时配置：

```yaml
jobrunr:
  background-job-server:
    poll-interval-in-seconds: 15
  jobs:
    default-number-of-retries: 3
```

### 10.4 任务执行状态在哪里查看？

- 文件系统中直接查看 `.md` 文件的 status 字段
- JobRunr Dashboard（内置 Web 控制台，默认 `/dashboard`）

## 十一、小结

求职派的任务调度体系围绕三个核心原则构建：

1. **AI 驱动**：任务不是硬编码的逻辑，而是由 LLM 动态执行的单元。`TaskHandler` 调用 `LlmCaller`，让 AI 自己决定如何完成任务。

2. **用户隔离**：每个 Task 和 RecurringTask 都强制绑定 `jobClawUserId`，文件系统按用户分目录存储，调度器和推送机制都按用户路由。

3. **分层解耦**：
   - `TaskTool` → Agent 工具层（LLM 可见）
   - `TaskManager` → 调度管理层（JobRunr）
   - `TaskHandler` → 任务执行层（LLM + 通知）
   - `FileSystemTaskRepository` → 存储层（文件系统）

**三种任务类型覆盖了 Agent 运行时的全部异步场景**：
- 一次性任务：用户说 "帮我查 X"，立即入队执行
- 延时任务：用户说 "明天提醒我 X"，定时触发
- 周期性任务：用户说 "每天早上推送 X"，Cron 周期触发

这套体系让 Agent 不再只是"口头答应"，而是真正具备了**编排和执行异步任务**的能力。
