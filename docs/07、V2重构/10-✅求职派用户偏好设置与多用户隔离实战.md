# ✅求职派用户偏好设置与多用户隔离实战

> 当多个用户通过不同 IM 渠道与求职派对话，系统怎么区分谁是谁？A 用户配置了 DeepSeek 模型，B 用户想用硅基流动，怎么在同一个系统里互不干扰？管理员给机器人设了"仅作者可用"，其他人发消息为什么直接被拒？本文完整记录求职派的用户偏好体系（文件 + 数据库双层配置）与多用户隔离方案（身份区分 → 权限管控 → 存储隔离），以及每项设计背后的推理过程。

---

## 一、为什么需要用户偏好与隔离？

### 1.1 没有偏好与隔离会怎样？

**场景还原**：

```
用户 A（钉钉）："把我的默认模型换成阿里通义千问"
用户 B（飞书）："帮我找北京的 Java 岗位"
```

**没有用户隔离的系统**：

```java
// 反例：全局共享一个模型配置
String response = llmCaller.call("global-model", prompt);
```

**问题**：

| 问题 | 后果 |
|------|------|
| **模型混用** | A 切了阿里模型，B 的回复也跑了阿里，B 却付着 DeepSeek 的费用 |
| **权限失控** | 任何人都能访问配置为"仅管理员"的机器人 |
| **数据互串** | B 的求职画像被误加载到 A 的对话上下文中 |
| **渠道无归属** | 推送给用户的消息不知道发到哪个聊天窗口 |
| **配置覆盖** | A 改了配置，B 的配置也被覆盖了 |

### 1.2 V2 的设计目标

> **如何在共享运行时中，让每个用户拥有独立的模型偏好、API Key、存储空间和渠道权限，实现多用户无感知隔离？**

四个核心诉求：

1. **身份区分**：每条消息都携带 `jobClawUserId`，作为后续一切隔离的根
2. **偏好独立**：每个用户可独立配置模型、API Key、采集器类型
3. **权限管控**：基于 `ChannelScope` 限制不同用户对机器人的访问级别
4. **存储隔离**：用户画像、对话历史按用户目录独立存储

## 二、整体架构

```
用户通过 IM 发送消息
  │
  ▼
Channel.adaptToReceive()
  │  ┌─ ChannelScope 权限校验 ─── 是否允许该用户访问？
  │  │   ├─ OWNER  → 仅机器主
  │  │   ├─ LOGIN  → 已绑定用户
  │  │   ├─ VIP    → VIP/ADMIN 用户
  │  │   └─ PUBLIC → 所有人（匿名用户创建临时 ID）
  │  │
  │  └─ jobClawUserId 产出 ───── 从此身份隔离正式开始
  │
  ▼
ChannelReceiveMessage (包含 jobClawUserId)
  │
  ▼
MsgRouter.onMessageReceived()
  │  │
  │  ├─ Step 1: 身份采集引用 jobClawUserId ──→ 读写 users/{userId}/ 下的独立文档
  │  ├─ Step 4: 模型解析引用 jobClawUserId ──→ ModelProviders.getModel(userId, type)
  │  │              │
  │  │              ├─ getUserPreference(userId)  // 先查 List<preference>，未命中查 DB
  │  │              └─ resolveModel(userId)        // 用户级 → 全局级 fallback
  │  │
  │  └─ Agent 执行引用 jobClawUserId ──→ 操作隔离的存储
  │
  ▼
响应回写
  │  └─ ChannelRegistry.getChannelRspBuilderAdapter(jobClawUserId, channel)
  │        ← heartbeat 映射将 jobClawUserId 绑定到具体的 IM 通道
  │
  ▼
用户收到回复（隔离验证完成）
```

### 2.1 隔离维度总览

| 维度 | 隔离方式 | 关键类 |
|------|----------|--------|
| **身份** | `jobClawUserId` 贯穿全链路 | `ChannelReceiveMessage` |
| **权限** | `ChannelScope` 四级别准入 | `ChannelConfig` |
| **模型** | 用户级偏好 → 全局 fallback | `AiUserPreferenceProperties` + `ModelProviders` |
| **API Key** | 用户级覆盖全局 | `UserPreferenceEntry.providers.apiKey` |
| **存储** | `workspace/users/{userId}/` | `UserAgentSoulManager` 等 |
| **心跳** | `{userId}:{channelName}` 映射 | `ChannelRegistry` |
| **对话内存** | `userId:conversationId` 为 key | `FileSystemChatMemoryRepository` |

## 三、身份区分：jobClawUserId

### 3.1 身份的产生

`jobClawUserId` 是用户在整个系统中的**唯一身份标识**，在 `Channel.adaptToReceive()` 阶段产出：

**钉钉通道的例子**（`DingDingBotChannel.java:140`）：

```java
ChannelConfig channelConfig = sdk.getDingDingBotAccount();

if (channelConfig.getScope() == ChannelScope.OWNER) {
    jobClawUserId = robotOwnerUserId;             // 机器主 ID
} else if (channelConfig.getScope() == ChannelScope.LOGIN) {
    jobClawUserId = String.valueOf(user.userId()); // 绑定的用户 ID
} else if (channelConfig.getScope() == ChannelScope.PUBLIC) {
    if (user == null) {
        jobClawUserId = "D-" + dingDingId;         // 匿名临时 ID
    } else {
        jobClawUserId = String.valueOf(user.userId());
    }
}
```

**三种身份来源**：

| 来源 | 格式 | 场景 |
|------|------|------|
| 求职派注册用户 | 数字 ID（如 `42`） | 已绑定的登录用户 |
| 机器主（OWNER） | 数字 ID | 机器人创建者本人 |
| 匿名用户（PUBLIC） | `D-{dingDingId}` / `F-{feishuId}` | 未绑定但可访问公开机器人的用户 |

### 3.2 身份的传递

`jobClawUserId` 被封装在每个消息模型中，贯穿全链路：

```java
ChannelReceiveMessage          → jobClawUserId
ChannelResponseMessage         → jobClawUserId
UserConversationInfo           → jobClawUserId (record)
MessageReceivedEvent           → originalMessage.jobClawUserId
```

后续所有隔离逻辑都基于这个 ID：

```java
// MsgRouter：身份采集隔离
identityAgent.triggerToCollectIdentity(conversationInfo, userMessage);
// → 内部读写 workspace/users/{jobClawUserId}/soul.md

// ModelProviders：模型隔离
ModelProviders.getModel(userId, ModelType.TEXT);
// → 先查用户偏好，未配置则 fallback 到全局

// ChannelRegistry：消息推送隔离
channelRegistry.getChannelRspBuilderAdapter(jobClawUserId, channelName);
// → 心跳表 key = "{jobClawUserId}:{channelName}"
```

### 3.3 推理与设计决策

**为什么 jobClawUserId 是 String 而不是 Long？**

虽然已注册用户的 ID 是数值，但匿名用户使用了 `D-xxx` 或 `F-xxx` 前缀。用 `String` 可以统一处理所有用户类型，不需要在代码里区分"是数字还是前缀"。

**为什么在 Channel 层产出身份而不是在 Router 层？**

IM 通道各自掌握用户身份的第一手信息（钉钉的 staffId、飞书的 openId），且需要调用各自 SDK 来查询绑定关系。在 Channel 层完成 `adaptToReceive()` 后，后续链路只需认 `jobClawUserId`，不需要再理解各渠道的身份协议。这也让 MsgRouter 和各 Agent 完全与渠道解耦。

## 四、权限管控：ChannelScope

### 4.1 四级 Scope 模型

定义在 `ChannelConfig.java`：

```java
public enum ChannelScope implements StringBaseEnum {
    OWNER("OWNER", "机器人的归属者的聊天渠道"),
    LOGIN("LOGIN", "用户登录的聊天渠道"),
    VIP("VIP", "VIP用户可以享受的聊天渠道"),
    PUBLIC("PUBLIC", "所有人都可以接入的聊天渠道"),
}
```

**Scope 的决策流程**（以飞书通道为例）：

```
飞书用户发送消息
  │
  ├─ OWNER → 用户是否为该机器人的拥有者？
  │     ├─ 是 → 放行，jobClawUserId = 机器主 ID
  │     └─ 否 → 拒绝，"这个机器人只为创作者本人服务"
  │
  ├─ LOGIN → 用户是否已绑定求职派账号？
  │     ├─ 是 → 放行，jobClawUserId = 绑定用户 ID
  │     └─ 否 → 拒绝，"请到个人中心绑定渠道"
  │
  ├─ VIP → 用户是否为 VIP/ADMIN？
  │     ├─ 是 → 放行，jobClawUserId = 绑定用户 ID
  │     └─ 否 → 拒绝，"请开通 VIP"
  │
  └─ PUBLIC → 所有人可访问
        ├─ 已绑定 → jobClawUserId = 绑定用户 ID
        └─ 未绑定 → jobClawUserId = "F-{openId}"（匿名）
```

### 4.2 Scope 的配置来源

每个机器人账号（ChannelConfig）独立配置 Scope，存储在数据库或配置文件中，可通过管理后台修改。例如：

```yaml
agent:
  channels:
    dingding:
      bot-1:
        scope: OWNER
        appId: xxx
      bot-2:
        scope: PUBLIC
        appId: yyy
```

### 4.3 推理与设计决策

**为什么不是开箱即用+登录，而是四层？**

真实部署中遇到的需求：

| 需求 | 对应 Scope |
|------|-----------|
| "这个机器人只给我自己用" | OWNER |
| "绑定了我的账号才能用" | LOGIN |
| "付费 VIP 才能用" | VIP |
| "所有人都可以用，先体验再注册" | PUBLIC |

这四种需求无法互相覆盖——OWNER 不是 PUBLIC 的子集，VIP 也不是 LOGIN 的子集。所以设计成并列的四层，每个机器人管理员可以按需选择。

**为什么拒绝消息在 Channel 层直接返回而不是走 MsgRouter？**

权限检查是 MsgRouter 之前的"门禁"。如果走到 MsgRouter 再检查，未经授权的消息已经消耗了事件总线资源。在 Channel 层直接 `errorResponse()` 返回，简单高效，未经授权的消息不会进入任何核心处理流程。

**为什么匿名用户要创建临时 ID 而不是强制注册？**

降低准入门槛。PUBLIC 场景下，用户可能只是想问一句"今天有什么岗位"，强制注册会让用户体验断崖式下跌。临时 ID 加上 `D-`/`F-` 前缀后，系统能正常运行所有功能（身份采集、对话历史写入等），只是无法享受"跨设备同步"和"VIP 模型"等增值服务。

## 五、用户偏好：AiUserPreferenceProperties

### 5.1 双层配置体系

求职派的用户偏好配置采用**文件 + 数据库**双层设计：

```
AiUserPreferenceProperties.getUserPreference(userId)
  │
  ├─ 1. 内存列表查找
  │     for (UserPreferenceEntry entry : preference) {
  │         if (entry.userId.equals(userId)) return entry;
  │     }
  │
  └─ 2. 未命中时查数据库
        if (NumberUtil.isNumber(userId)) {
            return aiUserPreferenceService.loadUserPreferenceConfiguration(userId);
        }
        return null; // 匿名用户没有 DB 配置
```

**为什么是双层？**

| 层 | 存储位置 | 适用场景 | 更新方式 |
|----|----------|----------|----------|
| 顶层（List） | `application.yml` 的 `agent.ai.preference` | 全局默认配置（如 `total` 用户）、少量固定配置 | 重启生效 |
| 底层（DB） | `ai_user_preference` 表 | 用户通过聊天界面修改的个人偏好 | 实时生效 （`PropertiesRefreshedEvent`） |

### 5.2 配置内容

`UserPreferenceEntry` 包含：

```json
{
  "userId": "42",
  "collector": "AI_BASED",        // 身份采集器类型
  "channels": ["dingding"],        // 优先推送通道
  "models": {
    "text": "deepseek#deepseek-flash",
    "vision": "deepseek#deepseek-flash",
    "tts": "...",
    "asr": "...",
    "image": "...",
    "embedding": "...",
    "video": "..."
  },
  "providers": {
    "deepseek": {
      "apiKey": "xxxx",           // 用户级 API Key
      "apiStyle": "openai",
      "baseUrl": "https://api.deepseek.com/",
      "models": [...]
    }
  }
}
```

### 5.3 模型解析链路

`ModelProviders.getModel(userId, modelType)` 的完整解析逻辑：

```
getModel("42", TEXT)
  │
  ├─ getUserPreference("42")
  │     ├─ 内存 List 中命中？→ 返回 entry
  │     └─ 未命中 → 查 DB → 返回 entry
  │
  ├─ 未找到配置？
  │     └─ getUserPreference("total") → 使用全局默认
  │
  ├─ 找到用户偏好模型 "deepseek#deepseek-flash"
  │     └─ 解析 provider + modelName
  │           ├─ 先在用户级 providers 中查找 (用户自己的 API Key)
  │           └─ 未命中 → 在全局 providers 中查找 (系统级 API Key)
  │
  └─ buildModel() → 创建模型实例 (缓存)
```

**Fallback 顺序**：

```
用户 ID 精准匹配 → "total" 全局默认 → provider 用户级 → provider 全局级
```

### 5.4 修改偏好的方式

用户通过 `PreferenceSettingBizAgent` 用自然语言修改偏好：

```
用户："帮我把默认模型切到 ali#qwen-max"
  │
  ▼
PreferenceSettingBizAgent.process()
  │
  ├─ 检查 userId 是否为数字（必须绑定用户才能用）
  ├─ 调用 Tool method: updateActiveModel("ali", "qwen-max", TEXT)
  │     ├─ entry.getModels().setText("ali#qwen-max")
  │     └─ aiUserPreferenceService.saveOrUpdate(userId, json)
  │           ├─ 写入 ai_user_preference 表
  │           └─ 发布 PropertiesRefreshedEvent
  │
  └─ 事件监听
        ModelProviders.registerUserPreferenceChangeCallback()
        → modelCache.clear()  // 清除模型缓存，下次调用重新构建
```

### 5.5 PropertiesRefreshedEvent 的发布与消费

```java
// 发布端：AiUserPreferenceService
entity = aiUserPreferenceRepository.saveAndFlush(entity);
eventPublisher.publishEvent(
    new PropertiesRefreshedEvent(this, AiUserPreferenceProperties.class)
);

// 消费端：ModelProviders
@Async
@EventListener
public void registerUserPreferenceChangeCallback(PropertiesRefreshedEvent event) {
    if (AiUserPreferenceProperties.class.equals(event.getPropertiesClz())) {
        modelCache.clear();  // 清除所有模型实例缓存
        log.info("User preference changed, clear user cache");
    }
}
```

### 5.6 推理与设计决策

**为什么选择 JSON 字段存储偏好而不是关系范式化？**

`UserPreferenceEntry` 是一个深度嵌套的结构：`providers → apiKey/models`，`models → 7 种模型类型`。如果用关系范式拆成 `user_preference`、`user_model`、`user_provider`、`user_provider_model` 四张表，查询一个用户的完整配置需要 4 次 JOIN，修改时需要跨表事务。

JSON 字段方案：

```
ai_user_preference 表
├─ id
├─ user_id        (唯一索引)
├─ preference     (LONGTEXT JSON)  ← 整棵树存一起
└─ create_time / update_time
```

优点是：读写都是一次操作，代码简单。缺点是：无法按子字段查询（实际没有这个需求）。

**为什么 List<preference> 配置在 application.yml 而不用纯 DB？**

这里有一个设计取舍：如果完全通过 DB 存储配置，系统启动时必须从 DB 加载所有用户的偏好才能正常工作，增加了启动依赖。文件配置的 `total` 用户作为"种籽数据"，确保系统即使没有 DB 也能以一个默认模型运行。

另一个原因：运维管理人员（非开发者）可以通过管理后台或直接改 DB 来配置用户偏好，而 `total` 用户的全局默认值保持在配置文件中，不容易被误修改。

**为什么清除整个 modelCache 而不是只清除变更用户的缓存？**

细粒度清除需要知道"哪个用户变更了"，但 `PropertiesRefreshedEvent` 目前没有携带 userId。清除整个缓存（`ConcurrentHashMap`）在实践中的代价很小——缓存会在下次请求时按需重建。与其增加事件传递 userId 的复杂度，不如用简单方案。

**为什么 PreferenceSettingBizAgent 只服务绑定用户？**

```java
if (!NumberUtil.isNumber(userConversationInfo.jobClawUserId())) {
    return "仅绑定求职派账号的用户才可以使用服务偏好配置Agent哦~";
}
```

匿名用户的临时 ID（`D-xxx`）没有对应的 DB 记录，也无法关联到 `ai_user_preference` 表。如果允许它们修改偏好，修改后的配置下次用另一个设备登录时也找不到。所以限制为只有数字 ID 的注册用户才能使用偏好设置。

## 六、存储隔离

### 6.1 文件存储按用户拆分

所有用户的持久化文件按 `{userId}` 目录隔离：

```
workspace/
├── agent.md                           ← 全局操作手册（共享）
└── users/
    ├── 42/                            ← 用户 42
    │   ├── soul.md                    ← AI 灵魂设定
    │   ├── user.md                    ← 用户画像
    │   ├── info.md                    ← AI 身份名片
    │   ├── episodic-memory.yaml       ← 情景记忆
    │   └── conversations/             ← 对话历史
    │       ├── 42_dingding_xxxx.yaml
    │       └── ...
    ├── D-abc123/                      ← 匿名用户
    │   └── ...
    └── 99/
        └── ...
```

每个 Manager 类都基于 `{userId}` 操作：

```java
// UserAgentSoulManager
private Path resolveSoulFile(String jobClawUserId) {
    return usersDir.resolve(jobClawUserId).resolve("soul.md");
}

// UserAgentInfoManager
private Path resolveInfoFile(String jobClawUserId) {
    return usersDir.resolve(jobClawUserId).resolve("info.md");
}

// UserIdentityManager
private Path resolveIdentityFile(String jobClawUserId) {
    return usersDir.resolve(jobClawUserId).resolve("user.md");
}
```

### 6.2 对话内存按用户隔离

多轮对话的 Chat Memory 同样以 `jobClawUserId:conversationId` 为 key 隔离：

```java
// FileSystemChatMemoryRepository
// 存储路径: workspace/users/{userId}/conversations/{conversationId}.yaml
// 同一用户的不同对话会话不共享，不同用户之间完全隔离
```

### 6.3 媒体文件按用户隔离

用户在 IM 中发送的图片、文件按用户目录下载：

```java
// DingDingBotChannel 或 FeiShuBotChannel
var tmpFile = localStorageHelper.autoDownloadFile(
    jobClawUserId, name(), downloadUrl, fileType
);
```

### 6.4 推理与设计决策

**为什么用文件系统而不是全用数据库？**

文件系统有三个数据库难以替代的优势：

1. **可直接编辑调试**：`workspace/users/42/soul.md` 可以直接用 VSCode 打开编辑，改完立即生效，不用写 SQL
2. **增量读取**：按需加载（`loadSoul()` 时才读文件），不需要一次加载所有用户数据
3. **可读性强**：Markdown 格式一目了然，方便排查问题

当然代价是分布式部署时文件不共享——但当前阶段单机部署够用。

**为什么对话历史按 `userId/conversations/` 而不是统一的 conversations 目录？**

两个原因：一是文件数量分摊——如果 1000 个用户各 100 次会话，分散到 1000 个目录，单个目录下的文件数可控；二是删除用户时可以 `rm -rf workspace/users/{userId}` 一步清理干净，不需要遍历全表。

## 七、消息推送的隔离：心跳机制

### 7.1 为什么需要心跳？

JobClaw 不仅被动回复用户消息，还**主动推送**消息（如定时任务提醒、职位推荐通知）。问题是：

> **系统知道要给用户推送消息，但不知道该发到哪个 IM 通道、发给谁（例如钉钉的哪个 staffId）？**

心跳机制就是为了在用户与通道之间建立映射关系。

### 7.2 心跳的建立

当用户主动发送消息时，`AbsChannel.processMessage()` 自动更新心跳：

```java
public void processMessage(MsgWrapper<T> msg) {
    var r = adaptToReceive(msg);
    if (r == null) return;

    var hasHeartbeat = channelRegistry.getChannelRspBuilderAdapter(
        r.getJobClawUserId(), r.getChannel()) == null;
    var tag = this.saveHeartBeatConfig(msg, hasHeartbeat);
    if (tag) {
        var func = buildHeartBeatCallback(msg.getJobClawUserId());
        channelRegistry.refreshChannelHeartBeatInfoIgnoreNull(
            msg.getJobClawUserId(), r.getChannel(), func);
    }
    reportToAgent(r);
}
```

心跳表的数据结构：

```
ChannelRegistry.channelResponseAdapters
  key:   "{jobClawUserId}:{channelName}"    // 如 "42:dingding"
  value: Function<Object, ChannelResponseMessage>
         // 这个 function 将任意 Object 转化为带用户身份信息的 ChannelResponseMessage
```

### 7.3 心跳的使用

后台主动推送时，通过心跳反向找到通道：

```java
// 后台任务要推送消息给用户 42
var adapter = channelRegistry.getChannelRspBuilderAdapter("42", "dingding");
if (adapter != null) {
    var message = adapter.apply(pushData);
    channelRegistry.getChannel("dingding").responseToUser(message);
}
```

### 7.4 推理与设计决策

**为什么心跳映射键是 `{userId}:{channelName}` 而不是 `{userId}`？**

一个用户可能同时通过钉钉和飞书与系统对话。如果用 `{userId}` 做键，只能记录最后一次活跃的通道。用 `{userId}:{channelName}` 可以同时维护多个通道的心跳——推送给用户的消息可以从所有可用通道中选择最优的一个（如用户配置的 `channels` 优先级）。

**为什么用 Function 而不是直接存 response 数据？**

心跳是"如何构建消息"的模板，不是"消息内容"本身。推送时内容不同（职位推荐、任务提醒、系统通知），但构建方式（toUserId、passThrough 等）由通道决定。用 `Function<Object, ChannelResponseMessage>` 可以在推送时传入实际数据，动态生成响应消息。

## 八、配置热更新：PropertiesRefreshedEvent

### 8.1 事件流程

```java
AiUserPreferenceService.saveOrUpdate(userId, json)
  │
  ├─ JPA: saveAndFlush(entity)
  │
  └─ eventPublisher.publishEvent(PropertiesRefreshedEvent)
        │
        ├─ ModelProviders.clearModelCache()
        │     → 下次 getModel(userId, type) 时从 DB 重新读取
        │
        └─ (可扩展其他监听器)
```

### 8.2 推理与设计决策

**为什么用 Spring Event 而不是直接调用 ModelProviders？**

解耦。未来可能有更多组件需要响应偏好变更，比如：

- 偏好变更后清理 LLM Caller 的 Prompt 模板缓存
- 偏好变更后通知前端刷新配置
- 偏好变更后触发身份重新采集

用事件机制，`AiUserPreferenceService` 不需要知道谁在监听，新增监听器也不需要修改保存逻辑。

**为什么是异步的？**

`saveOrUpdate()` 已在事务中，如果同步调用 `modelCache.clear()` 不影响事务。但如果将来监听器变多或变慢（比如清 Redis 缓存），同步会拖慢整个保存操作。`@Async` 让偏好保存立即返回，缓存清理在后台完成。

## 十、总结

### 10.1 隔离体系总览

```
                 ┌──────────────────┐
                 │  IM 消息到达      │
                 │  (钉钉/飞书/微信)  │
                 └───────┬──────────┘
                         │
                 ┌───────▼──────────┐
                 │ ChannelScope     │  ← 权限隔离：OWNER/LOGIN/VIP/PUBLIC
                 │ 身份注入          │
                 └───────┬──────────┘
                         │
                 ┌───────▼──────────┐
                 │ jobClawUserId     │  ← 身份隔离：贯穿全链路
                 │ 作为唯一标识       │
                 └───────┬──────────┘
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
     ┌──────────┐ ┌──────────┐ ┌──────────┐
     │ 模型偏好  │ │ 文件存储  │ │ 对话内存  │
     │ 用户级→   │ │ users/   │ │ userId:  │
     │ 全局fall  │ │ {userId}/│ │ convId   │
     └──────────┘ └──────────┘ └──────────┘
```

### 10.2 核心设计原则回顾

| 原则 | 体现在哪 | 为什么 |
|------|----------|--------|
| **身份前置** | `jobClawUserId` 在 Channel 层产出，后续全链路复用 | 后续模块不需要理解各渠道的身份协议 |
| **门禁前置** | Scope 校验在 adaptToReceive 中完成，不进入核心流程 | 无效消息不消耗系统资源 |
| **先文件后 DB** | 配置查询先走内存 List，未命中再查 DB | 减少启动依赖，保障核心功能可用 |
| **用户级 → 全局级 fallback** | 模型解析先查用户偏好，未配置则用 `total` 默认 | 用户不需要配完所有参数才能用 |
| **配置即代码** | Preferences 修改通过聊天对话完成（自然语言） | 不需要用户学习管理后台 |
| **事件驱动热更新** | `PropertiesRefreshedEvent` 让配置修改后即时生效 | 用户不需要重启服务或重连 |

### 10.3 可以改进的方向

1. **配置缓存细粒度清除**：当前清除整个 `modelCache`，可以改为只清除变更用户的缓存项
2. **Scope 级联配置**：当前每个 ChannelConfig 独立设置 Scope，可以支持"如果 Scope 未设置，继承父级"的模式
3. **多用户偏好合并**：当前每个用户完全独立，可以支持团队/企业级别的"共享模型配额 + 个人偏好"模式
4. **心跳过期机制**：当前心跳只在用户发送消息时刷新，如果用户长时间不活跃，心跳可能失效（但无自动清理）
5. **匿名用户升级**：匿名用户注册后，`D-xxx` ID 需要合并到数字 ID 中，目前需要手动迁移数据
