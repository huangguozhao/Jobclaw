前面几篇文章聊的都是大模型的“文本能力”，对话、结构化返回、上下文管理，都围绕着 ChatModel 展开。

但 Spring AI 能做的事情远不止文本对话。从 2.0 版本开始，图像生成有了一套独立的接口体系 ImageModel，和 ChatModel 走的是完全不同的 API 路径。

![](https://cdn.paicoding.com/stutymore/11-SpringAI-image-model-overview-20260726084535-8740c5cc.png)

这篇文章从 ImageModel 的接口设计讲起，再拆解求职派是怎么把图像模型接入到了多供应商架构中，最后回答一个容易搞混的问题，IMAGE 和 VISION 到底有什么区别。

## 01、ImageModel 和 ChatModel 有什么不同？

ChatModel 大家已经很熟悉了。输入是一段对话（Prompt），输出也是一段文字（ChatResponse）。

ImageModel 的逻辑完全不同。它接收一段文字描述（ImagePrompt），返回一张图片的 URL 或 Base64 数据（ImageResponse）。

![](https://cdn.paicoding.com/stutymore/11-SpringAI-chat-vs-image-model-20260726084747-e7600062.png)

一个是“文字进文字出”，另一个是“文字进图片出”。

两者在 Spring AI 的类型体系里也是彻底隔离的。Spring AI 2.0 把所有模型抽象成了一个泛型接口 `Model<TReq, TRes>`，ChatModel 和 ImageModel 分别继承了它，但泛型参数完全不同。

```java
// 聊天模型：对话进，文字出
public interface ChatModel 
    extends Model<Prompt, ChatResponse>

// 图像模型：文字进，图片出
public interface ImageModel 
    extends Model<ImagePrompt, ImageResponse>
```

除了类型不同，两者走的 HTTP 端点也不一样。

聊天模型请求的是 `/v1/chat/completions`，图像模型请求的是 `/v1/images/generations`。

求职派的模型配置里（`ModelConfig.java`），这两个路径由 `completionsPath` 和 `imagesPath` 两个独立的字段分别维护。

不管是 OpenAI 还是阿里百炼，聊天和生图都是两个独立的 API，请求参数、返回结构、计费方式全都不一样。

对于开发者来说，这种分离的好处在于心智模型很清晰。写聊天相关的代码时，只需要关注 ChatModel 体系里的那些类（Prompt、ChatResponse、ChatOptions）。

写图像生成的代码时，切换到 ImageModel 体系（ImagePrompt、ImageResponse、ImageOptions）。两套 API 独立演进，互不干扰。

## 02、怎么用 ImageModel 生成一张图？

核心调用只需要三步。构建一个图像提示词，调用图像模型的 `call` 方法，从返回结果里取出图片 URL。

```java
ImagePrompt prompt = new ImagePrompt(
    "一只穿西装的龙虾，正在参加求职面试",
    OpenAiImageOptions.builder()
        .model("Kwai-Kolors/Kolors")
        .build());
ImageResponse response = imageModel.call(prompt);
String url = response.getResult()
    .getOutput().getUrl();
```

ImagePrompt 接收两个参数，一段文字描述和一组图像选项。

选项里最关键的是 `model` 字段，用来指定具体使用哪个图像生成模型。求职派的供应商配置里，硅基流动的生图模型是 `Kwai-Kolors/Kolors`；阿里百炼则通过 DashScope 的图像接口接入，模型名同样在供应商的模型清单里维护。

![](https://cdn.paicoding.com/stutymore/11-SpringAI-image-prompt-structure-20260726084911-63461f96.png)

需要注意的一点，不同供应商的实现类是不同的。

走 OpenAI 兼容协议的供应商（硅基流动、OpenAI 官方等）统一用 `OpenAiImageOptions`，阿里百炼用 `DashScopeImageOptions`。它们都实现了 Spring AI 的 `ImageOptions` 接口，但各自有一些供应商特有的扩展参数。

核心参数倒是一致的，模型名、图片尺寸（width/height）、生成风格（style）、返回格式（responseFormat）。所以切换供应商的时候，只需要换一下 Options 的实现类和模型名，业务代码基本不用动。

![](https://cdn.paicoding.com/stutymore/11-SpringAI-image-call-flow-20260726085032-eeb560d5.png)

调用 `imageModel.call(prompt)` 之后，返回的 ImageResponse 里包含了图像生成的完整结果。通过 `response.getResult().getOutput()` 可以拿到一个 Image 对象，里面有图片的 URL 和 Base64 编码数据。

大多数供应商返回的是 URL，需要业务代码自己去下载图片内容。

还有一个容易忽略的细节是 `model` 参数。Spring AI 的 Options 允许不传模型名，但一旦不传，最终落到哪个模型就取决于供应商侧的默认行为，而不是你在后台供应商配置里写的那一个。

所以求职派的构建方法里一律显式传入，`AliModelProvider.buildImageModel()` 和 `OpenAiModelProvider.buildImageModel()` 都会把 `info.getModelName()` 放进 Options，配置里写的是什么模型，请求里发出的就是什么模型。

如果使用的是早期版本的 Spring AI（1.0.0 时代），调用方式会有区别。当时有一个通用的 `ImageOptionsBuilder` 类来构建选项参数。

到了 Spring AI 2.0，这个类已经被移除了，改成了供应商各自的 Options Builder。从旧版本升级过来的话，需要把 `ImageOptionsBuilder.builder()` 换成对应供应商的 Builder。

下面是一张实际生成的效果图。

![](https://github.com/liuyueyi/spring-ai-demo/raw/master/docs/static/11-4.webp)

卡通风格的效果还算不错，换成写实风格会差一些。日常做示意图、封面图这类场景，已经够用了。

## 03、求职派怎么把图像模型接入多供应商架构？

求职派里支持图像生成的供应商有阿里百炼和一批 OpenAI 兼容平台（硅基流动、OpenAI 官方等），它们都通过同一套供应商接口接入。顺带说一句，DeepSeek 只提供文本和多模态理解能力，没有文生图模型，所以图像生成不会走 `deepseek` 供应商。

这套多供应商架构的核心有两个东西，一个是模型类型枚举，一个是供应商接口。

![](https://cdn.paicoding.com/stutymore/11-SpringAI-seven-model-types-20260726085151-f5e73b58.png)

先看模型类型。求职派在模型配置中定义了 7 种模型类型。

- **TEXT**：纯文本聊天
- **VISION**：视觉理解
- **IMAGE**：图像生成
- **VIDEO**：视频生成
- **EMBEDDING**：文本嵌入
- **ASR**：语音识别
- **TTS**：语音合成

IMAGE 就是图像生成模型的类型标识。

当业务代码需要获取一个图像模型时，调用路径是这样的。先通过模型解析器读取用户配置的模型偏好（格式为 `provider#modelName`，比如 `silicon#Kwai-Kolors/Kolors`），然后根据 provider 找到对应的供应商模块，最后调用供应商的 `model()` 方法构建出具体的 ImageModel 实例。

整个过程和获取聊天模型的流程完全一致，只是最终构建出来的结果类型不同。

这种统一的解析流程意味着，图像模型也可以享受到和聊天模型相同的用户偏好机制和模型缓存机制。用户可以在管理后台配置自己偏好的图像生成模型，系统会自动解析并缓存模型实例，不用每次都重新创建。

每个供应商模块都实现了统一的供应商接口，里面有一个 `model()` 方法，用 Java 21 的 switch 表达式按类型分发到不同的构建方法。以阿里百炼供应商为例（`AliModelProvider.java`）。

```java
public Model model(ModelConfig.ModelInfo info) {
    return switch (info.getType()) {
        case TEXT -> buildChatModel(info);
        case VISION -> buildChatModel(info);
        case IMAGE -> buildImageModel(info);
        // EMBEDDING、ASR、TTS 等省略
    };
}
```

TEXT 和 VISION 都走同一个聊天模型的构建方法，因为视觉理解本质上还是基于 ChatModel（只是输入里多了一张图片作为 Media 附件）。

但 IMAGE 走的是一条独立的路径，单独调用图像模型的构建方法。

回到多供应商的主题上来。不同供应商的图像模型构建方式，各有各的特点。

阿里百炼走的是 DashScope 专属的图像 API 类和图像模型类，`baseUrl` 和 API Key 都取自供应商配置，模型名则来自模型清单。

```java
DashScopeImageApi api = DashScopeImageApi.builder()
    .apiKey(info.getApiKey())
    .baseUrl(info.getBaseUrl())
    .restClientBuilder(...)
    .build();
DashScopeImageModel model = DashScopeImageModel.builder()
    .dashScopeApi(api)
    .defaultOptions(DashScopeImageOptions.builder()
        .model(info.getModelName()).build())
    .build();
```

阿里的实现额外注入了 `ObservationRegistry`（可观测性注册表），每次图像生成调用都会被记录到监控指标里，方便在线上排查问题。

走 OpenAI 兼容协议的供应商则由 `OpenAiModelProvider` 统一构建 `OpenAiImageModel`，通过配置里的 `baseUrl` 和 `imagesPath` 指到各自的图像接口，硅基流动的 Kolors 就是这么接进来的。

## 04、为什么图像模型不走 LLM 调用接口？

看完了多供应商的接入方案，可能有小伙伴会问，求职派的业务 Agent 不是都通过 LLM 调用接口来调用大模型的吗？ImageModel 为什么不走这条路？

先看一下 LLM 调用接口的定义（`LlmCaller.java`）。

```java
public interface LlmCaller {
    String call(UserConversationInfo user, 
                Prompt prompt);
    Flux<String> stream(
        UserConversationInfo user, Prompt prompt);
}
```

入参是 Prompt（聊天用的），出参是 String 或文字流。

ImageModel 的入参是 ImagePrompt，出参是 ImageResponse。

但类型不匹配只是表面原因，类型的问题完全可以通过泛型或者方法重载来解决。

更深层的原因在于，聊天和生图的调用场景有本质差异。

![](https://cdn.paicoding.com/stutymore/11-SpringAI-llm-layers-vs-image-model-20260726085437-aae48cab.png)

求职派的 LLM 调用接口有三层实现，从基础到高级逐层叠加了这些能力。

第一层是基础调用器，负责模型解析和基本的请求发送。

第二层是业务 Agent 调用器，叠加了上下文记忆管理、系统提示词注入和工具调用。

第三层是用户偏好调用器，进一步加载了用户画像信息。

举个例子。当用户在微信上问“帮我推荐 Java 岗位”时，LLM 调用接口会自动把之前的对话历史加载进上下文，让大模型记住用户之前说的“薪资 25k 以上”。

同时还会注入系统提示词，告诉大模型“你是一个求职助手”。第三层甚至会把用户的技能画像（Java 高级、3 年经验）也一并传入。

这些能力对聊天对话来说是必需的。

但图像生成完全不需要这些。用户说“帮我画一只龙虾”，模型就画一只龙虾。

不需要知道上一轮对话说了什么，不需要知道用户是什么身份，更不需要调用外部工具去查数据库。

这就是一个典型的无状态操作。

把它硬塞进 LLM 调用接口体系，要么加一堆“如果是图像模型就跳过”的分支判断，要么给 ImageModel 也包上一层完全用不到的记忆和工具管理。两种做法都会引入不必要的复杂度。

所以求职派的做法是，图像模型通过模型解析器直接获取，业务代码自己调用 `imageModel.call(prompt)` 就行了。不需要经过 LLM 调用接口这层封装。

职责划分清晰，比什么都往一个接口里塞要好维护得多。

## 05、IMAGE 和 VISION 到底有什么区别？

这是很多初学者容易搞混的一个概念。尤其是在求职派的源码里，有一个叫 `IMAGE_MODEL` 的枚举值被映射成了 VISION 类型，这更容易让人困惑。

先说结论。

**IMAGE** 是文字生图，输入一段描述，输出一张新图片，用的是 ImageModel。

**VISION** 是图片理解，输入一张图片加一个问题，输出文字回答，用的是 ChatModel（带图片附件）。

两者的方向完全相反。IMAGE 从文字到图片，VISION 从图片到文字。

![](https://cdn.paicoding.com/stutymore/11-SpringAI-image-vs-vision-20260726085558-b8c9e71d.png)

求职派的岗位采集模块用的就是 VISION，不是 IMAGE。

它接收一张岗位截图，调用视觉理解模型提取里面的结构化信息（公司名、岗位名、薪资范围），然后存入数据库。这个过程走的是 ChatModel + Media 附件，而不是 ImageModel。

具体来说，VISION 模式下的调用方式是在 Prompt 里附带一个 Media 对象，把图片的 URL 或者 Base64 数据塞进去。

大模型看到图片后，会根据文字提问来分析图片内容。比如给一张招聘信息的截图，配上一句“请提取这张图里的公司名和薪资范围”，模型就会返回结构化的文字结果。

这和 IMAGE 模式完全是两回事。IMAGE 模式下压根就没有图片输入，输入只有文字描述。

IMAGE 是“无中生有”，VISION 是“看图说话”。搞清楚这一点，就不会在选择模型类型的时候犯迷糊了。

在采集模块的代码里，有一个叫 `IMAGE_MODEL` 的枚举值被映射成了 VISION 类型。

```java
return type == GatherModelTypeEnum.IMAGE_MODEL 
    ? ModelConfig.ModelType.VISION 
    : ModelConfig.ModelType.TEXT;
```

这行代码第一眼看起来像 bug。IMAGE_MODEL 怎么映射到了 VISION？

但它的语义是正确的。岗位采集模块需要的“图像模型”是一个“能看懂图片”的模型，不是一个“能画出图片”的模型。

命名上用了 IMAGE 是因为处理的输入是图片，但能力上需要的是 VISION（视觉理解）。

这也解释了为什么供应商接口的 switch 里，TEXT 和 VISION 走的都是聊天模型的构建方法。因为 VISION 本质上就是一个“增强版的聊天”，只不过对话里带上了一张图片。

IMAGE 和 VISION 虽然都跟图片打交道，但解决的是完全不同的问题。下一篇多模态文章会详细展开 VISION 的用法，到时候大家就能更清楚地感受到两者的差异了。

### 如何把求职派写到简历上？

项目名称：求职派（JobClaw）

项目简介：基于 Spring AI 2.0 和 LangGraph4J 的多 Agent 求职系统，支持微信/钉钉/飞书多渠道接入，实现智能岗位推荐、用户画像采集和意图分类路由。

技术栈：Java 21、Spring Boot 4.0、Spring AI 2.0、LangGraph4J、JPA/Hibernate、React 19/Next.js 15

核心职责：

- 基于 Spring AI 的 ImageModel 接口实现了多供应商图像模型的统一接入，支持阿里百炼、OpenAI 兼容平台（硅基流动等）的动态切换，新增供应商只需实现供应商接口即可自动注册
- 设计了 7 种模型类型（文本/视觉/图像/视频/嵌入/语音识别/语音合成）和多级模型解析机制，支持按用户偏好动态切换模型供应商和具体型号
- 封装了三层 LLM 调用器架构（基础调用、业务 Agent 调用、用户偏好调用），实现上下文记忆管理、系统提示词注入和工具调用的逐层叠加，聊天模型和图像模型职责清晰分离
- 基于视觉理解模型实现了岗位截图的结构化信息提取，将非结构化的岗位图片自动解析为公司名、岗位名、薪资范围等关键字段，提升岗位数据入库效率
- 实现了兼容 OpenAI 协议的第三方供应商接入方案，通过自定义 baseUrl 和 imagesPath 参数支持硅基流动等平台的无缝对接
