不得不承认，AI 进化的太快了。

MCP Server 教程已经烂大街了，看了一圈下来，十篇有八篇在教你写一个"查询当前时间"的 demo——加个 `@Tool` 注解，配一段 YAML，用 Trae 或者 Cursor 连上去试一把，完事。

但真到了生产环境就会发现，demo 到生产有一堆问题。

工具不是一个两个，可能有几十个，它们分散在不同模块里，怎么统一注册？

同一个应用既要对外暴露工具（当 Server），又要接入外部的 MCP 服务（当 Client），这两个角色怎么共存？

服务重启之后，已经连上的 MCP 客户端会话全部丢失了，怎么恢复？

![](https://cdn.paicoding.com/stutymore/07-✅07.实现一个MCPServer-20260714163309.png)

这篇内容就用求职派的源码做证据，从 Spring AI 的三步实现讲起，一直拆到生产环境要解决的会话恢复问题。

## 01、MCP 到底在解决什么问题

MCP 的全称是 Model Context Protocol，由 Anthropic 在 2024 年底开源。

一句话说清楚它的定位，**给大模型提供一个统一的工具接入标准，不用再为每个外部系统单独写适配代码。**

用 USB 来类比最直观。一台裸主机只能开关机，但插上键盘、鼠标、摄像头，就能打字、拍照、视频通话——前提是这些外设都遵守了 USB 协议。

![](https://cdn.paicoding.com/stutymore/07-✅07.实现一个MCPServer-20260716101829.png)

MCP 做的事和 USB 一样，只不过面对的不是外设，而是大模型需要调用的各种工具和数据源。

MCP 遵循客户端-服务端架构，一个主机可以连接多个 MCP Server。

![](https://cdn.paicoding.com/stutymore/07-✅07.实现一个MCPServer-20260716100020.png)

整个协议的工作流程可以拆成 7 步。

1. 用户在客户端发起一个问题
2. 客户端把问题传给大模型
3. 大模型分析问题，决定调用哪个工具
4. 通过 MCP 协议，把工具调用指令发到服务端
5. 服务端执行工具，把结果返回给大模型
6. 大模型基于工具返回的结果生成最终回答
7. 回答通过客户端展示给用户

![](https://cdn.paicoding.com/stutymore/07-✅07.实现一个MCPServer-20260716100044.png)

对求职派来说，MCP 解决了这样一个痛点。

岗位数据的能力需要对外开放。求职派自己有岗位推荐、岗位检索、数据采集等工具，如果 Claude Desktop、Cursor、Trae 这些客户端想调用这些能力，按传统做法得一个个写 API 适配。

![](https://cdn.paicoding.com/stutymore/07-mcp-server-flow-20260714163749-02031891.png)

有了 MCP，只要把这些工具按协议标准暴露出来，任何支持 MCP 的客户端都能直接接入。

## 02、Spring AI 实现 MCP Server

Spring AI 对 MCP 协议做了完整的封装，实现一个 MCP Server 的步骤非常简单。

### 第一步，加依赖

在 `pom.xml` 里引入 `spring-ai-starter-mcp-server-webmvc`，它会自动配置好 SSE 端点和消息处理通道。

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-mcp-server-webmvc</artifactId>
</dependency>
```

![](https://cdn.paicoding.com/stutymore/07-mcp-pom-dependencies-20260714163914-d1318363.png)

这个 starter 是基于 WebMVC 的 SSE 协议实现通信的，适合传统 Servlet 应用。

如果项目用的是 WebFlux，对应的 starter 是 `spring-ai-starter-mcp-server-webflux`。

### 第二步，用 @Tool 声明工具方法

在求职派里，岗位推荐是最核心的 MCP 工具。来看它的实现（`app/.../oc/mcp/OcMcpService.java`）。

```java
@Tool(description = "根据输入的用户求职意愿信息，返回满足条件的职位列表给用户")
public List<OcVo> queryRecommendOcListForUser(McpReqDto req) {
    OcSearchReq search = new OcSearchReq();
    // 将 MCP 请求参数映射到搜索条件
    search.setPage(1);
    search.setSize(20);
    return ocService.searchOcList(search).getList();
}
```

`@Tool` 注解的 `description` 是大模型判断要不要调用这个工具的唯一依据。描述写得含糊，大模型就不知道什么时候该调用这个工具。

工具方法的参数通过 `@ToolParam` 来声明，每个参数都需要一段描述（`app/.../oc/mcp/model/McpReqDto.java`）。

```java
@Data
public class McpReqDto {
    @ToolParam(description = "招聘类型：春招、秋招、暑期实习、日常实习、社招", required = false)
    private String recruitmentType;
    @ToolParam(description = "职位名称：如研发工程师、运营等", required = false)
    private String position;
}
```

这些描述会随 MCP 协议的工具列表一起发给大模型，大模型根据用户的自然语言输入，自动映射到对应的参数值。

用户说"帮我看看武汉有什么央企的秋招"，大模型就会把 `jobLocation` 填成"武汉"，`companyType` 填成"央国企"，`recruitmentType` 填成"秋招"。

### 第三步，注册为 MCP 工具

光有 `@Tool` 注解还不够，需要通过一个工具回调提供者把它注册到 MCP Server 里（`app/.../oc/mcp/OcMcpConfiguration.java`）。

```java
@Configuration
public class OcMcpConfiguration {
    @Bean
    public ToolCallbackProvider dateProvider(OcMcpService dateService) {
        return MethodToolCallbackProvider.builder()
            .toolObjects(dateService).build();
    }
}
```

`MethodToolCallbackProvider` 会扫描传入对象上所有带 `@Tool` 注解的方法，自动创建回调处理器并注册到 Spring AI 的工具框架里。

Spring AI 的自动配置在启动时会收集所有的工具回调提供者 Bean，统一暴露给 MCP Server。

最后在 `application.yml` 里配置 MCP Server 的基本信息。

```yaml
spring:
  ai:
    mcp:
      server:
        name: 求职派
        protocol: STATELESS
        type: sync
        sse-endpoint: /api/sse
        sse-message-endpoint: /api/mcp/messages
```

![](https://cdn.paicoding.com/stutymore/07-mcp-yaml-config-20260714164218-3fd8f81d.png)

其中：

- `sse-endpoint` 是 MCP 客户端建立 SSE 连接的入口
- `sse-message-endpoint` 是客户端发送工具调用请求的端点
- `protocol: STATELESS` 表示无状态通信，每次请求独立处理，不维持长连接状态。

启动应用后，访问 `/api/sse` 就能看到 MCP Server 已经在等待连接了。

![](https://cdn.paicoding.com/stutymore/07-✅07.实现一个MCPServer-20260716100433.png)

## 03、求职派有哪些 MCP 工具

求职派对外暴露了 20 多个 MCP 工具，按功能域分成了 5 个类别。

| 功能域 | 工具 | 所在模块 | 做什么 |
|--------|------|----------|--------|
| 岗位推荐 | 按求职意愿查岗位 | app/oc | 根据招聘类型、地点、岗位等条件返回匹配的校招信息 |
| 岗位推荐 | 智能岗位检索 | plugins/job-library | 基于用户偏好的智能匹配，支持多维度筛选 |
| 岗位采集 | 从URL抓取岗位 | agents/job-fetch | 爬取招聘网站，提取结构化岗位数据 |
| 岗位采集 | 从文本/文件提取岗位 | agents/job-fetch | 支持从文本、本地文件、图片中提取岗位信息 |
| 岗位管理 | 查询/更新/发布草稿 | agents/job-fetch | 草稿岗位的审核、修改和正式发布 |
| 浏览器操作 | 导航/点击/填表/截图 | plugins/playwright | 基于 Playwright 的网页自动化 |
| 任务调度 | 创建/调度/删除任务 | core | 支持一次性和 cron 定时任务 |
| 计划管理 | 创建计划/更新子任务 | plugins/plan-notebook | 多步骤计划的创建和进度跟踪 |
| MCP 管理 | 动态注册 MCP Server | core | 运行时注册新的 HTTP 或 stdio 类型 MCP Server |

这些工具分散在不同的 Maven 模块里。

![](https://cdn.paicoding.com/stutymore/07-mcp-tool-modules-20260714164404-58a60221.png)

`app/oc` 放岗位业务工具，`plugins/` 放通用插件，`agents/` 放业务 Agent 的专用工具，`core` 放基础工具。

每个模块自己定义 `@Tool` 方法和工具回调提供者 Bean，Spring AI 在启动时自动收集并统一注册。

这种模块化的组织方式有一个好处，新增一类工具时，只要在对应模块里加 `@Tool` 方法和注册 Bean，不需要动 MCP Server 的任何配置。

## 04、怎么同时当 Server 和 Client

求职派有一个有趣的设计，它不仅对外暴露了 MCP 工具（当 Server），同时还作为 MCP Client 接入了外部的 MCP 服务。

![](https://cdn.paicoding.com/stutymore/07-mcp-dual-role-20260714164706-cbe79f26.png)

同一个 Spring Boot 应用里，Server 和 Client 并存。

要实现这一点，在 `pom.xml` 里同时引入两个依赖就行了。

```xml
<artifactId>spring-ai-starter-mcp-server-webmvc</artifactId>
<!-- 同时引入 Client -->
<artifactId>spring-ai-starter-mcp-client</artifactId>
```

Client 端的配置写在 `application-ai.yaml` 里。

```yaml
spring:
  ai:
    mcp:
      client:
        stdio:
          servers-configuration: ${MCP_SERVERS_CONFIG:classpath:mcp-servers.json}
        enabled: ${AGENT_MCP_CLIENT_ENABLED:false}
        type: async
```

`mcp-servers.json` 定义了要连接的外部 MCP Server 列表。

求职派通过 stdio 协议接入了 Selenium MCP（网页自动化）和 Wenyan MCP（微信公众号发布）两个外部服务。

### 自动发布公众号

这个 Server/Client 双角色架构最典型的应用场景，是求职派的公众号自动发布功能。

![](https://cdn.paicoding.com/stutymore/07-mcp-wechat-publish-20260714164852-4da804b9.png)

整个流程分三步。

先查询当天新上架的校招岗位（用的是 Server 端的岗位数据），把它们拼成 Markdown 格式的文章，然后通过 ChatClient 调用大模型，大模型自动调用 Wenyan MCP（这是 Client 端接入的外部服务），把文章推送到微信公众号草稿箱。

来看核心代码（`app/.../oc/mcp/WechatBlogPublishService.java`）。

```java
return this.ocAiModelContext.getMainChatClient()
        .prompt()
        .system("你是一个善于发布公众号的专家，请基于工具调用来实现发布")
        .user(promp)
        .call().content();
```

代码只有 4 行，但背后串联了两个角色。

大模型通过 MCP Client 调用外部的微信公众号发布工具，而文章内容则来自本地的岗位数据服务。Server 提供数据，Client 消费外部能力，大模型在中间做调度。

求职派还做了一个更大胆的设计，允许大模型在运行时动态注册新的 MCP Server。

核心模块里有一个 MCP 管理工具，大模型可以通过工具调用把一个新的 HTTP 或 stdio 类型的 MCP Server 写入配置，重启后生效。

这意味着大模型不仅能使用工具，还能给自己"装新工具"。

## 05、生产环境绕不开的坑：会话恢复

demo 教程不会告诉你的一个问题，MCP 客户端和服务端之间的连接是有状态的。

![](https://cdn.paicoding.com/stutymore/07-mcp-session-recovery-20260714165041-73e807d1.png)

客户端第一次连上来时，会发一个 `initialize` 请求做协议协商，然后发一个 `notifications/initialized` 通知确认完成。

这两步完成后，会话才算建立。

问题来了，服务端一旦重启，内存里的会话状态就会全部丢失。客户端的 SSE 连接断开后会重连，但新的连接没有经过初始化流程，服务端不认它，工具调用就会失败。

![](https://cdn.paicoding.com/stutymore/07-mcp-client-entity-20260714165310-037bb677.png)

求职派的解法是把会话的握手信息持久化到数据库里。当客户端发来 `initialize` 和 `notifications/initialized` 请求时，把请求参数保存下来。

```java
public void saveSessionInfo(String sessionId, String initInfo, String notifyInfo) {
    McpClientEntity entity = mcpClientRepository.findBySessionId(sessionId);
    if (entity == null) {
        entity = new McpClientEntity();
        entity.setSessionId(sessionId);
        entity.setUserId(ReqInfoContext.getReqInfo().getUserId());
    }
    // 保存初始化参数和通知参数
    mcpClientRepository.save(entity);
}
```

当客户端重连后发来工具调用请求时，服务端检测到会话未初始化，就从数据库里取出之前保存的握手参数，自动重放一次初始化流程。

接下来的问题是，怎么判断会话是否已经初始化了？

Spring AI 的会话对象没有提供公开的状态查询方法，求职派用了反射来读取内部的 `state` 字段。

```java
Field field = session.getClass().getDeclaredField("state");
field.setAccessible(true);
AtomicInteger value = (AtomicInteger) field.get(session);
if (value.get() == 0) {
    // state == 0 表示未初始化，需要从数据库恢复
}
```

用反射访问框架内部状态不是一个优雅的方案，但在 Spring AI 没有暴露公开 API 之前，这是能拿到会话状态的唯一方式。

还有一个边界情况需要处理。

服务端重启后，客户端重新请求 `/api/sse` 建立连接，这时候会生成一个新的 sessionId，和数据库里保存的不一样。

求职派的兜底策略是，按 sessionId 查不到时，退回到按 userId 查最近一条会话记录，用它来恢复初始化。这个方案在单用户场景下没问题，多设备同时连接时可能会有冲突，但对当前的业务规模已经够用了。

**MCP 协议本身是无状态的通信格式，但会话的建立过程是有状态的——这个区别，只有踩过坑才知道。**

## 如何把求职派写到简历上？

项目名称：求职派（JobClaw）

项目简介：OpenClaw 风格的多 Agent 求职系统，支持微信/钉钉/飞书多渠道接入，通过 MCP 协议对外暴露岗位推荐、数据采集、浏览器自动化等 20+ 工具能力。

技术栈：Java 21、Spring Boot 4.0、Spring AI 2.0、MCP 协议、LangGraph4J、JPA/Hibernate、React 19 / Next.js 15

核心职责：

- 基于 Spring AI 的 `@Tool` + `MethodToolCallbackProvider` 机制实现 MCP Server，对外暴露岗位推荐、智能检索、浏览器操作等 20+ 工具，支持 Claude、Cursor、Trae 等主流 MCP 客户端接入
- 设计 MCP Server/Client 双角色架构，同一应用内既暴露本地工具能力，又通过 stdio/HTTP 协议接入 Selenium、微信公众号发布等外部 MCP 服务，实现跨服务工具编排
- 实现 MCP 会话持久化恢复机制，将客户端初始化握手参数存储到 MySQL，服务重启后自动重放初始化流程，客户端无感知恢复连接
- 基于模块化工具注册架构，将 MCP 工具按功能域分布在 app/oc、plugins、agents、core 四个 Maven 模块，通过 Spring AI 自动发现机制统一注册，新增工具零配置接入
- 实现公众号自动发布流水线，通过 ChatClient 调度大模型，串联本地岗位数据查询（MCP Server 端）与微信公众号发布（MCP Client 端），每日自动生成并推送校招快讯
