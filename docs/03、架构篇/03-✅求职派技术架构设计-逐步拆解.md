这篇内容将从分层的角度，逐步拆解求职派的技术架构是怎么搭起来的。

先来看主要的技术选型。

![](https://cdn.paicoding.com/stutymore/03-✅求职派技术架构设计-逐步拆解-20260702083037.png)

详细表单：

| 维度 | 选型 | 版本 |
|------|------|------|
| 后端框架 | Spring Boot | 4.0.5 |
| Java 版本 | Java 21 | records、pattern matching、virtual threads |
| AI 接入 | Spring AI | 2.0.0-M4 |
| 智能体框架 | LangGraph4J | 1.6.0-rc4 |
| ORM | Spring Data JPA + Hibernate | — |
| 开发数据库 | H2（嵌入式） | — |
| 生产数据库 | MySQL + Liquibase | — |
| 任务调度 | JobRunr | 8.5.1 |
| 浏览器自动化 | Playwright | 1.52.0 |
| 认证 | JWT（Auth0 java-jwt） | 4.4.0 |

Spring AI 2.0.0-M4 是里程碑版本。选它是因为 Spring 生态的集成度高，大模型调用、工具注册、结构化输出、MCP 协议都有现成的封装。

LangGraph4J 是用来编排多步骤 Agent 工作流的。

求职派的岗位数据处理流程包括任务分类、数据采集、数据清洗、数据发布。

用 LangGraph4J 的状态图来编排，每一步都是图上的一个节点，节点之间有条件分支。比如采集结果为空就直接终止。

大模型处理网页链接时，简单的爬虫只能拿到 HTML 源码，遇到 JavaScript 动态渲染的页面就无能为力了。

Playwright 能启动真实的浏览器，等页面渲染完再抓取内容。求职派把它封装成了一个独立的插件模块，通过 MCP 工具协议暴露给大模型按需调用。

求职派在 Maven 层面做了多模块拆分。

- **核心层**，对话管理、Agent 抽象、路由、模型、记忆
- **渠道层**，微信、钉钉、飞书三个独立模块
- **Agent 层**，身份采集、岗位抓取、岗位推荐各自独立
- **供应商层**，OpenAI、阿里、Anthropic 三个独立模块
- **插件层**，Playwright 浏览器自动化、岗位检索等
- **主应用**，Web 管理后台、职位数据、用户、支付、MCP Server
- **前端**，React + Next.js，静态导出后部署到 Spring Boot 的 static 目录

![](https://cdn.paicoding.com/stutymore/03-✅求职派技术架构设计-逐步拆解-20260702083134.png)

求职派对外提供三种视图，页面、REST API、MCP Server。

页面是 Next.js 构建的前端，静态导出后放到 static 目录下，由 Spring MVC 的静态资源机制提供访问。

REST API 是标准的 Spring MVC 控制器，所有接口统一以 `/api/` 开头。按业务分了十几个控制器，覆盖管理后台的岗位管理、草稿管理、字典配置、用户管理、大模型监控，也有用户侧的使用量查询和公共的字典接口。

MCP Server 是 Spring AI 提供的能力，基于流式 HTTP 协议，让外部 AI 工具（比如 Claude Code、Cursor）能直接调用求职派的岗位查询、信息采集等能力。MCP 端点跑在 `/api/mcp`，同时提供 SSE 端点用于长连接推送。

SSE 在求职派里用得很多。

管理后台提交采集任务后，任务在后台异步执行，前端通过 SSE 长连接实时接收每一步的执行状态——正在分类、正在采集、采集了多少条、清洗完成。

MCP Server 也走 SSE 推送，外部 AI 工具调用求职派能力时，能实时拿到中间结果。

![](https://cdn.paicoding.com/stutymore/03-✅求职派技术架构设计-逐步拆解-20260702083158.png)

求职派的鉴权策略有两种。

- **HTTP API 请求**，基于 JWT 做身份认证。用户登录后拿到 token，后续每个请求在 Header 里带上 token，服务端用拦截器校验。JWT 的签发者、密钥、过期时间都可以通过环境变量配置，默认过期时间 30 天
- **MCP 请求**，基于 HTTP Authorization 头做身份认证，协议本身是无状态的（STATELESS），每个请求包含认证信息

权限控制走的是自定义注解 + 拦截器的方式。

控制器方法上标注权限注解，声明需要什么角色（管理员、普通用户、所有人），拦截器在请求进来时校验当前用户的角色是否匹配。

上下文管理用了阿里开源的 TransmittableThreadLocal（TTL）。普通的 ThreadLocal 在线程池里会丢失上下文，TTL 能自动在线程切换时传递上下文信息。

求职派的异步工具类在创建线程池时，用 TTL 的包装器把线程池包一层，所有提交到线程池的任务都能拿到原始请求的上下文（用户信息、请求头等）。

这一点在异步调大模型时很重要。采集任务从调度器线程发起，调大模型时可能切到另一个线程，如果上下文丢了，就不知道是哪个用户发起的请求，也没法按用户偏好选模型。

![](https://cdn.paicoding.com/stutymore/03-✅求职派技术架构设计-逐步拆解-20260702083216.png)

数据库分环境管理，开发、测试、生产各用不同的配置。

| 环境 | 数据库 | Schema 管理 | DDL 模式 |
|------|--------|-------------|----------|
| 开发 | H2（嵌入式文件数据库） | JPA 自动更新 | update |
| 测试 | MySQL | Liquibase 迁移 | none |
| 生产 | MySQL | Liquibase 迁移 | none |

开发环境用 H2 有一个好处，项目 clone 下来不需要装 MySQL，不需要建库建表，启动就能跑。H2 的数据文件存在 `workspace/datas/` 目录下，重启不会丢。种子数据库直接附带在仓库里，复制一份就能用。

测试和生产环境用 MySQL + Liquibase。Liquibase 的变更日志（changelog）记录了所有的 Schema 变更，每次部署自动比对并执行未执行的迁移脚本。

开发环境不需要 Liquibase，因为 JPA 的 `ddl-auto: update` 会自动根据实体类更新表结构。

ORM 用 Spring Data JPA，实体类用 JPA 注解标注，命名策略是驼峰转下划线（Java 的 `companyName` 对应数据库的 `company_name`）。

数据访问层的代码组织按"实体类 → 仓库接口 → 服务类 → 转换器"的结构分包，实体和业务对象之间用转换器做映射，服务类不直接暴露数据库实体。

除了关系型数据库，求职派还有一部分数据用文件系统存储。

用户的身份信息（三层画像，基本信息、技能经验、职业性格）存在 `workspace/users/{userId}/` 目录下，格式是 Markdown。对话历史存在 `workspace/conversations/{userId}/` 下，格式是 YAML。

文件存储目前用本地文件系统，用户上传的 CSV、Excel、图片存在本地目录，路径持久化到数据库。

![](https://cdn.paicoding.com/stutymore/03-✅求职派技术架构设计-逐步拆解-20260702083233.png)

Maven 配置了三个环境 Profile，dev（默认）、test、prod。通过 `-P` 参数切换，每个 Profile 加载对应的配置文件。

配置文件按顺序加载：

`application.yml` → `application-ai.yaml`（AI 相关）→ `application-dal.yaml`（数据库相关）→ `application-private.yml`（本地覆盖，git 忽略）。

敏感信息（API Key、数据库密码）放在环境变量或 private 配置里，不进版本库。

前端的构建和部署集成在一起。

`pnpm run deploy` 会先构建 Next.js 的静态导出，然后把产物复制到 `app/src/main/resources/static/` 目录。打 JAR 包时静态资源一起打进去，部署时一个 JAR 包就包含前后端所有内容。

![](https://cdn.paicoding.com/stutymore/03-✅求职派技术架构设计-逐步拆解-20260702083304.png)

服务默认跑在 8087 端口，JobRunr 的任务调度仪表盘跑在 8099 端口。JobRunr 配置了 1 个 Worker 线程，和前面提到的免费模型并发限制对应——同一时间只处理一个后台任务。

Spring Boot Actuator 开放了 health、info、metrics 端点，用于健康检查和基础监控。
