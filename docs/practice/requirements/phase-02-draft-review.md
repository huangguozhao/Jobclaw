# 第 02 期：岗位草稿审核与发布

**依赖**：第 01 期  
**目标**：建立从待审核内容到正式岗位的人工运营闭环。

## 业务背景

岗位不能直接进入公开目录。运营人员需要先录入草稿、修正字段、判断重复和有效性，再决定发布或驳回。

## 用户故事

- 作为运营人员，我能创建、编辑、查询和删除尚未发布的草稿。
- 作为审核人员，我能看到原始内容和结构化字段的差异。
- 作为审核人员，我能发布合格草稿，或填写原因后驳回。
- 作为负责人，我能知道谁在什么时间做了关键操作。

## 业务规则

1. 草稿状态至少包含待审核、已驳回、已发布；状态迁移必须受规则约束。
2. 发布前校验公司、岗位名称、申请地址和来源；失败时不得生成半条正式岗位。
3. 同一来源中的相同岗位不能重复发布。重复判定规则由技术设计提出并说明误判策略。
4. 已发布草稿不能再次发布；重复请求应返回第一次发布结果或明确的幂等响应。
5. 删除只允许作用于未发布草稿；关键操作记录操作者、时间和原因。
6. 草稿编辑存在并发覆盖风险，必须提供版本冲突检测或等价保护。

## 范围外

自动采集、AI 解析、复杂审批流和批量发布。

## 验收场景

- Given 一条字段完整的待审核草稿，When 审核人发布，Then 同一事务内生成正式岗位并更新草稿状态。
- Given 发布过程发生数据库错误，When 事务结束，Then 草稿和正式岗位均不处于部分成功状态。
- Given 两名审核人同时编辑同一草稿，When 后提交者保存旧版本，Then 系统提示冲突。
- Given 已发布草稿，When 再次提交发布，Then 不会生成重复岗位。
- Given 驳回草稿时未填写原因，When 提交，Then 请求被拒绝。

## 非功能要求

后台接口全部要求授权；审计记录不可由普通编辑操作覆盖；表格支持长文本截断与详情展开。

## 设计评审问题

- 状态迁移规则放在哪里才能被所有入口复用？
- 去重键如何兼顾同一公司同名岗位的不同批次？
- 发布后的正式岗位允许直接修改吗？

## 交付物

草稿模型、状态迁移设计、后台接口与页面、发布事务、并发保护、审计记录和验收报告。
