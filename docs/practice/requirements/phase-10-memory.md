# 第 10 期：会话记忆与上下文管理

**依赖**：第 09 期  
**目标**：在模型上下文有限的情况下保持多轮对话连续性，并可靠保存会话历史。

## 业务背景

完整对话会持续增长，直接发送全部历史会超出模型窗口并增加成本。系统需要保存原始历史，同时为每次调用选择近期消息和必要摘要。

## 用户故事

- 作为用户，我刷新或重连后仍能继续之前的会话。
- 作为用户，长对话中早期关键约束不会无故丢失。
- 作为开发者，我能解释一次模型调用实际注入了哪些上下文。
- 作为用户，我能清空当前会话，而不会影响其他会话。

## 业务规则

1. 会话按求职用户、渠道和会话标识隔离；群聊还需区分真实发送者策略。
2. 原始消息持久化保留角色、时间、内容类型和关联 ID，写入必须防止并发损坏。
3. 工作记忆按可配置窗口选取近期消息，并为系统 Prompt 和当前输入保留预算。
4. 超出窗口的历史可生成会话摘要；摘要必须标明覆盖范围，不能重复摘要同一批消息。
5. 摘要失败不阻塞当前对话，系统退回纯窗口策略并记录失败。
6. 清空会话需要明确作用域；不同智能体是否共享上下文由设计说明。
7. 附件大文本不能未经限制完整写入每次模型上下文。

## 范围外

跨会话语义检索、用户画像自动更新和向量数据库。

## 验收场景

- Given 会话已有多轮消息，When 进程重启后继续聊天，Then 历史仍可读取。
- Given 历史超过窗口，When 构建上下文，Then 总预算不超限且包含近期消息。
- Given 两个会话并发写入，When 完成，Then 文件或数据库均可解析且互不串话。
- Given 摘要模型超时，When 用户发送新消息，Then 对话仍能通过降级策略完成。
- Given 用户重置一个会话，When 查看另一个会话，Then 另一个会话不受影响。

## 非功能要求

持久化采用原子写或事务；上下文组装可重复测试；记录 token 估算、裁剪和摘要触发原因。

## 设计评审问题

- 原始历史、工作记忆和摘要分别是什么事实来源？
- 摘要由同步请求触发还是异步后台生成？
- 文件存储达到什么规模后需要迁移，接口如何保留演进空间？

## 交付物

会话模型、记忆存储、窗口算法、摘要机制、重置功能、并发与恢复测试、上下文调试视图。
