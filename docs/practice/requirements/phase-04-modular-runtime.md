# 第 04 期：多模块工程重构

**依赖**：第 03 期  
**目标**：把可运行的业务单体重构为清晰的装配层、共享运行时和可插拔能力模块。

## 业务背景

团队将新增多种消息渠道、模型供应商、工具和业务智能体。如果所有代码继续堆在主应用中，每次扩展都会影响无关业务，测试也会越来越依赖完整应用启动。

## 架构需求

1. 主应用负责进程启动、Web 接口和最终装配，不承载通用的渠道、模型或智能体实现。
2. 共享运行时只定义稳定契约和公共机制，不依赖任何具体渠道、供应商或业务智能体。
3. 渠道、供应商、工具和业务智能体形成独立模块，可以被主应用按需组合。
4. 依赖方向必须单向：具体模块依赖共享契约，共享契约不反向依赖具体实现。
5. 模块缺席时，主应用可以明确降级或启动失败；行为必须被文档说明。
6. 至少选择一项现有功能迁移，证明重构前后用户行为保持一致。

## 范围外

微服务拆分、远程调用、插件市场、运行期下载代码和复杂模块版本治理。

## 验收场景

- Given 只构建共享运行时，When 执行测试，Then 不需要启动主应用或数据库业务模块。
- Given 新建一个示例能力模块，When 主应用引入依赖，Then 能被自动发现或显式装配。
- Given 移除示例能力模块，When 启动主应用，Then 其他功能仍可用且日志说明能力缺失。
- Given 执行依赖检查，Then 不存在共享运行时依赖具体实现的循环。
- Given 重构前的第 01～03 期验收集，When 重构完成，Then 行为仍然通过。

## 非功能要求

模块接口保持小而稳定；调用者不需要理解实现内部配置；每个模块有独立测试入口和职责说明。

## 设计评审问题

- 哪些概念是真正跨模块共享，哪些只是暂时重复？
- 自动发现和显式装配如何取舍？
- 当前只有一个实现的地方是否真的需要接口？

## 交付物

模块关系图、依赖规则、重构后的构建结构、至少一个迁移案例、架构测试和回归报告。
