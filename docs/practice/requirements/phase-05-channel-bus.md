# 第 05 期：统一消息模型与事件总线

**依赖**：第 04 期  
**目标**：让不同消息入口使用同一条内部处理链路，并让接收与响应解耦。

## 业务背景

用户未来会从网页、微信、钉钉和飞书发送文本、图片或文件。业务处理不能为每个平台复制一套逻辑，也不能依赖平台 SDK 的对象结构。

## 用户故事

- 作为渠道开发者，我只需把平台消息适配为统一消息，就能进入业务处理链路。
- 作为业务开发者，我不需要知道消息来自哪个 SDK，也能读取用户、会话和内容。
- 作为渠道，我能收到统一响应事件并转换为平台允许的格式。

## 业务规则

1. 接收消息至少表达消息 ID、渠道、渠道账号、发送者、会话、私聊或群聊、内容、附件和时间。
2. 响应消息必须能关联原请求，并表达文本、流式片段、思考状态、工具状态和错误结束。
3. 同一渠道消息 ID 重复到达时，业务处理最多执行一次或产生可证明等价的结果。
4. 消息接收、业务处理和消息发送通过事件解耦；监听器失败必须可观察。
5. 平台 SDK 类型不得越过渠道适配模块的接口。
6. 群聊和私聊必须在统一模型中明确区分，为后续权限和画像策略提供依据。

## 范围外

真实 IM 平台、LLM、多 Agent 路由和消息持久化历史。

## 验收场景

- Given 两种格式不同的模拟渠道消息，When 经过各自适配器，Then 得到语义一致的内部消息。
- Given 同一消息被重复投递，When 进入处理链路，Then 不会执行两次业务副作用。
- Given 业务处理发布响应，When 渠道监听到事件，Then 响应发送到正确的渠道账号和会话。
- Given 某个监听器抛出异常，When 事件完成，Then 异常可定位且不会造成无限重试。
- Given 群聊消息，When 进入业务层，Then 可可靠识别群聊属性和真实发送者。

## 非功能要求

统一消息模型可序列化；事件日志带关联 ID；适配器测试不依赖真实网络；明确同步与异步监听的线程和上下文传播规则。

## 设计评审问题

- 事件总线是进程内机制还是持久消息队列？当前需求需要哪一种？
- 去重状态保存在哪里，生命周期多长？
- 附件应该进入消息体、引用对象还是独立存储？

## 交付物

消息契约、渠道接口、两个模拟适配器、事件发布与监听、去重策略、链路测试和时序图。
