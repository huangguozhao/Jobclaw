# 第 14 期：岗位检索与个性化推荐

**依赖**：第 13 期  
**目标**：基于正式岗位和用户画像提供可解释、可反馈的推荐结果。

## 业务背景

关键词搜索只能回答用户明确表达的条件。推荐需要综合城市、岗位方向、学历、技能、时间和用户反馈，同时让用户理解为什么推荐或排除某岗位。

## 用户故事

- 作为用户，我能用自然语言或结构化条件检索岗位。
- 作为用户，我能获得一组带匹配理由和风险提示的推荐。
- 作为用户，我能对结果标记感兴趣、不感兴趣或已投递。
- 作为产品人员，我能评估推荐覆盖率和用户反馈，而不暴露个人隐私。

## 业务规则

1. 候选召回只使用已发布且有效的岗位，并先执行确定性硬条件过滤。
2. 推荐结果至少解释匹配项、缺失信息和潜在冲突；理由不得捏造岗位或画像中不存在的事实。
3. 没有完整画像时仍可基于当前查询推荐，并明确缺少哪些信息。
4. 相同输入在岗位数据和配置不变时，应产生稳定候选集合；生成式模型可润色理由但不能越权改变硬过滤结果。
5. 反馈记录用户、岗位、动作、时间和来源；重复反馈遵循明确的覆盖或追加规则。
6. 已明确不感兴趣的岗位默认不再次推荐，除非用户清除反馈或岗位发生实质更新。
7. 返回数量有上限，并说明排序依据。

## 范围外

机器学习排序模型、跨用户协同过滤、自动投递和简历改写。

## 验收场景

- Given 用户要求杭州实习，When 推荐，Then 不出现其他城市的正式岗位，除非用户允许远程或多城市。
- Given 用户画像缺少学历，When 岗位要求硕士，Then 结果提示未知风险而不是宣称匹配。
- Given 用户标记某岗位不感兴趣，When 再次请求相同推荐，Then 默认不返回该岗位。
- Given 模型在理由中添加不存在的福利，When 结果校验，Then 该理由被拒绝或纠正。
- Given 无任何候选，When 返回结果，Then 解释限制条件并允许用户放宽筛选。

## 非功能要求

推荐请求有候选数量和耗时指标；硬过滤逻辑可纯测试；反馈数据按用户隔离并支持删除。

## 设计评审问题

- 哪些是硬条件，哪些是软偏好？由谁配置？
- 解释来自规则还是模型，如何验证事实性？
- 岗位更新到什么程度应重新向曾拒绝的用户展示？

## 交付物

检索模块、召回与排序规则、推荐智能体、解释校验、反馈接口与页面、离线用例集和验收报告。
