# 第 06 期：WebSocket 对话闭环

**依赖**：第 05 期  
**目标**：在网页端建立可认证、可恢复、支持流式状态的实时对话。

## 业务背景

网页用户希望直接与 JobClaw 对话。服务端处理可能持续数秒，并逐步返回思考、工具执行和正文片段，因此普通一次性 HTTP 响应无法提供良好体验。

## 用户故事

- 作为用户，我能建立实时连接并发送消息。
- 作为用户，我能看到消息发送、处理中、流式输出、完成和失败状态。
- 作为用户，短暂断线后可以恢复连接，不会把同一条消息执行两次。
- 作为开发者，我能用本地回声处理器验证完整链路。

## 业务规则

1. 建立连接时识别用户或访客身份，连接不能声明成其他用户。
2. 客户端消息必须携带客户端生成的唯一 ID；重连重发时服务端按该 ID 幂等。
3. 服务端事件至少包含确认接收、正文片段、处理完成和处理失败；事件顺序可验证。
4. 一个用户可有多个页面连接；响应必须发往正确会话，不广播给其他用户。
5. 连接断开要释放会话资源；服务端对空闲连接和异常客户端设有上限。
6. 第一版使用确定性的本地回声或规则处理，不依赖真实模型。

## 范围外

模型调用、语音、图片理解、跨节点 WebSocket 会话共享。

## 验收场景

- Given 用户已连接，When 发送消息，Then 依次收到确认、一个或多个内容事件和完成事件。
- Given 用户 A 与 B 同时连接，When A 发送消息，Then B 不会收到 A 的响应。
- Given 客户端在完成前断线并重发同一消息 ID，When 服务端恢复，Then 业务只执行一次。
- Given 连接携带伪造用户标识，When 握手，Then 服务端拒绝或以可信认证身份覆盖。
- Given 服务端处理异常，When 流终止，Then 客户端显示可重试错误并结束加载状态。

## 非功能要求

单机目标支持 200 个空闲连接；慢客户端不得无限占用内存；事件和日志共享消息关联 ID。

## 设计评审问题

- 使用原生 WebSocket、STOMP 还是 SSE，各自怎样满足双向通信？
- 流式事件的顺序号和重放窗口如何设计？
- 多标签页与多设备算同一会话还是不同会话？

## 交付物

实时协议、服务端连接管理、网页聊天窗、本地处理器、断线与幂等测试、浏览器验收记录。
