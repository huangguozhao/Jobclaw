# JobClaw 成品项目分析

## 结论

JobClaw 已经具备完整演示所需的主要链路，可以视为一个“功能完成度较高的实战项目”。它同时保留了持续演进中的痕迹：旧的岗位业务、管理后台与新的多 Agent 运行时并存，自动化测试和生产化治理仍有补强空间。因此，它很适合作为练手参考实现，不适合被当作无需判断即可照搬的标准答案。

## 当前产品能力

### 求职业务

- 公开岗位浏览、分类和查询；
- 岗位草稿管理、审核和发布；
- 文本、网页、CSV、Excel、图片等来源的岗位采集；
- AI 结构化提取、职位库检索和岗位推荐；
- 用户、会员、充值、优惠券和个人偏好；
- 管理后台、模型供应商配置和调用监控。

### 智能体运行时

- 微信、钉钉、飞书和 WebSocket 渠道；
- 统一内部消息与进程内事件总线；
- 业务智能体注册、意图识别、路由、会话绑定和系统命令；
- OpenAI 风格、阿里和 Anthropic 模型适配；
- 同步与流式 LLM 调用、ReAct 中间件和工具；
- 文件会话、上下文窗口、摘要、情景记忆和三层用户画像；
- 一次性、周期性和计划任务。

## 架构观察

根 Maven 工程将 `core`、`channels`、`providers`、`plugins`、`agents` 和 `app` 组合起来。`app` 是最终装配层，也承载岗位、用户、采集、配置和 Web 管理业务。前端位于 `ui-react`，采用 Next.js 静态导出后部署到 Spring Boot。

运行时最重要的三个接缝是：

1. 渠道把平台消息适配为内部消息，并通过事件进入路由；
2. 路由根据命令、画像状态、会话绑定和意图选择业务智能体；
3. 智能体通过统一调用层解析用户模型偏好、注入记忆并调用工具。

消息主链路可以概括为：

```text
外部消息
  → 渠道适配
  → 消息事件
  → 系统命令 / 身份采集
  → 意图识别与会话绑定
  → 业务智能体
  → 模型与工具
  → 响应事件
  → 原渠道
```

## 值得学习的设计

- 渠道、模型供应商和业务智能体都有明确扩展位置，适合学习端口与适配器思想。
- 普通岗位业务先形成可用产品，再叠加 AI 能力，业务价值不完全依赖模型。
- 草稿与正式岗位分离，为不确定的 AI 输出建立人工审核缓冲区。
- 用户级模型偏好、会话隔离和渠道身份绑定体现了多用户运行时的真实复杂度。
- 记忆被拆成近期上下文、摘要、情景事实和画像，而不是把所有历史直接塞给模型。

## 需要带着判断阅读的部分

- `app` 同时承担装配和较多历史业务，部分共享逻辑的归属仍可讨论。
- 文件系统承担会话和部分任务存储，适合本地和小规模场景，但并发、查询和多实例部署需要重新设计。
- 生产代码规模明显大于自动化测试规模。练习版本应补足模块测试和端到端验收。
- 前端构建配置允许忽略 TypeScript 和 ESLint 错误，这降低了构建门禁强度。
- 原有 `docs/plan.md` 混合了已完成、进行中和历史设想，个别说明可能落后于最新源码。
- 外部 IM、模型、支付和网页采集带来凭据、限流、SSRF、Prompt 注入、媒体安全及幂等风险，需要专门治理。

## 为什么按 19 期拆分

训练路线先交付普通岗位产品，再引入运行时抽象，随后逐步加入模型、工具、Agent、记忆和数据流水线，最后处理外部渠道与生产化。这样每个新概念都有真实需求推动，避免一开始就设计大量没有第二个实现的接口。

每一期只增加一类主要复杂度，并要求保留可演示闭环。例如第 05 期只解决消息抽象与事件，第 07 期只解决供应商差异，第 09 期才引入 Agent 路由。这个顺序让设计错误更容易暴露，也方便在里程碑处比较重构前后的收益。

## 建议的练习仓库策略

把当前目录保留为只读参考，新建一个练习仓库。练习仓库从第 00 期开始，只复制需求文档和必要的素材样例；每期验收后打标签，例如 `phase-03-accepted`。这样既能独立思考，也能随时回到成品实现做差异复盘。
