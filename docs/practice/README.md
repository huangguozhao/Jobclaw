# JobClaw 实战研发训练营

这套文档把现有 JobClaw 成品拆成一条可重复实践的产品研发路线。目标不是照抄源码，而是让练习者经历需求澄清、领域建模、方案评审、编码、测试、验收和复盘的完整过程。

## 推荐使用方式

当前仓库作为“参考实现”保留。真正练习时，建议创建一个新的 Git 仓库，从第 00 期开始逐期实现。每一期只阅读对应需求文档；完成设计和第一版实现后，再查看本目录的 `coach-reference.md`，对照成品源码复盘。

每期固定走六个关卡：

1. **需求澄清**：列出歧义、假设、风险和不做的范围。
2. **技术设计**：使用 `templates/technical-design-template.md` 写设计，不直接开始编码。
3. **设计评审**：解释领域模型、模块接口、异常策略、数据一致性和测试计划。
4. **开发交付**：小步提交，保留可运行状态。
5. **需求验收**：逐条执行 Given/When/Then 验收场景。
6. **迭代复盘**：记录判断失误、返工原因、可复用经验和技术债。

## 训练原则

- 需求文档描述“为什么、做什么、做到什么程度”，技术设计由练习者负责。
- 每一期都必须有一个能独立演示的业务闭环。
- 新抽象必须由真实变化支撑。只有一个实现时，先避免为了扩展性制造空接口。
- 测试穿过模块接口验证业务结果，避免绑定内部方法和私有状态。
- 遇到源码现状和需求冲突时，以当期需求为准，并在复盘中记录差异。
- 外部模型、IM 平台和支付能力必须提供本地替身，保证没有真实凭据也能验收主流程。

## 完成标准

完成全部迭代后，练习者应能独立解释并实现：

- 一个从岗位数据到用户使用界面的完整业务系统；
- 一个支持多渠道、多模型、多 Agent 的消息运行时；
- 会话记忆、用户画像、工具调用和计划任务；
- 数据审核、权限、监控、错误恢复和安全控制；
- 前后端联调、自动化测试、发布检查和线上问题定位。
