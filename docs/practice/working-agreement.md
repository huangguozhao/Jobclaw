# 协作与交付规则

## 角色分工

练习者担任需求分析师、架构师和开发工程师，对方案选择和代码质量负责。AI 担任产品经理、评审人和测试负责人：解释需求、追问设计、审查实现、设计验收场景，但在练习者提交方案前不主动给出成品源码答案。

## 每期输入

每期只向练习者提供：业务背景、目标、用户故事、业务规则、范围、验收场景、非功能要求和约束。需求中故意保留少量需要澄清的决策点，用于训练提问和权衡能力。

## 每期必须交付

1. 一份技术设计文档；
2. 可运行的代码；
3. 自动化测试和必要的手工验证记录；
4. README 或运行说明更新；
5. 一份验收报告；
6. 一份简短复盘。

## 评审门禁

### 需求门禁

- 已明确用户、使用场景和成功指标；
- 已列出范围外事项；
- 已回答需求中的开放问题，或记录合理假设；
- 关键名词与 `CONTEXT.md` 一致。

### 设计门禁

- 画出主流程和失败流程；
- 说明数据模型及生命周期；
- 说明模块接口及依赖方向；
- 说明并发、幂等、事务、重试和权限策略；
- 测试计划能覆盖业务结果，而非只覆盖方法行数。

### 发布门禁

- 验收场景全部通过；
- 错误信息可理解，日志可定位问题；
- 不把密钥、个人信息和测试数据提交进仓库；
- 新环境能按文档启动；
- 已知问题已记录并给出影响范围。

## 分支与提交建议

每一期使用独立分支，例如 `phase/03-user-auth`。一次提交只表达一个完整意图，推荐使用 `feat:`、`fix:`、`test:`、`docs:`、`refactor:` 前缀。合并前保留设计评审和验收记录。

当前下载目录没有 `.git` 元数据。正式练习开始前，应先为练习仓库初始化 Git，并提交一个只包含可运行骨架的基线版本。

## AI 辅导约定

当练习者说“给我本期需求”时，只展开需求和澄清问题。当练习者说“评审我的设计”时，优先指出遗漏、风险和替代方案，不代写完整实现。当练习者说“验收”时，按需求文档逐条检查真实运行结果。当练习者明确要求参考答案时，才使用成品源码作对照。
